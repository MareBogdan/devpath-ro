# Sisteme Multi-Agent

Un singur agent AI, oricât de bine promtat, are limitări. Poate executa sarcini secvențiale, dar nu poate lucra în paralel pe mai multe fronturi simultan. Nu poate fi expert profund în toate domeniile simultan. Nu poate critica propriul output cu adevărat obiectiv. Sistemele multi-agent rezolvă aceste limitări prin specializare și coordonare.

## De ce multi-agent: divide și cucerește

Gândiți-vă cum funcționează o firmă eficientă. Nu angajezi o singură persoană care să facă totul — angajezi specialiști: un cercetător care adună informații, un analist care le interpretează, un writer care redactează, un editor care verifică. Fiecare face ce face cel mai bine. Rezultatul colectiv depășește ce ar putea produce oricine singur.

Sistemele multi-agent aplică același principiu AI-ului:

**Specializare:** Fiecare agent este optimizat pentru o sarcină specifică. Un agent de cercetare nu trebuie să scrie frumos. Un agent de scriere nu trebuie să verifice fapte.

**Paralelism:** Mai mulți agenți pot lucra simultan pe sub-sarcini independente.

**Verificare reciprocă:** Un agent poate critica și corecta output-ul altui agent — eliminând "blind spots" pe care auto-critica nu le poate detecta.

**Scalabilitate:** Poți adăuga sau înlocui agenți fără a rescrie tot sistemul.

## Arhitectura Orchestrator + Worker

Cel mai comun pattern este ierarhia Orchestrator-Worker:

**Orchestratorul** este managerul. Primește sarcina de nivel înalt, o descompune în sub-sarcini, le distribuie workerilor, colectează rezultatele și sintetizează outputul final. Nu face muncă de execuție — coordonează.

**Workerii** sunt specialiștii. Fiecare primește o sub-sarcină bine definită, o execută și returnează rezultatul într-un format standardizat. Nu gândesc strategic — execută eficient.

**Exemplu concret — pipeline pentru articol de blog:**
- Orchestratorul primește: "Scrie un articol de 800 de cuvinte despre beneficiile muncii remote"
- Worker 1 (Researcher): caută statistici recente și studii despre munca remote
- Worker 2 (Outliner): structurează articolul pe baza cercetării
- Worker 3 (Writer): scrie articolul conform structurii cu datele cercetate
- Worker 4 (Editor): verifică, corectează și îmbunătățește textul

## Tipuri de pipeline-uri

**Pipeline secvențial:** Output-ul unui agent devine input pentru următorul. Simplu de implementat, dar nu beneficiază de paralelism.

```
ResearcherAgent → AnalystAgent → WriterAgent → EditorAgent
```

**Pipeline paralel:** Mai mulți agenți lucrează simultan pe sub-sarcini independente, rezultatele sunt reunite.

```
ResearcherAgent (sursele A-D) ─┐
ResearcherAgent (sursele E-H) ─┤→ MergeAgent → WriterAgent
ResearcherAgent (sursele I-L) ─┘
```

**Pipeline ierarhic:** Agenți manager care coordonează sub-agenți, care la rândul lor pot coordona alți sub-agenți.

## Prompting-ul orchestratorului

Orchestratorul are nevoie de un prompt care să îi definească: rolul de coordonare, workerii disponibili, formatul de comunicare și cum să sintetizeze.

```
Ești orchestratorul unui sistem de analiză competitivă. Ai 3 agenți worker disponibili:
- ResearcherAgent: caută informații publice pe web și le returnează ca date brute structurate
- AnalystAgent: analizează date și identifică pattern-uri, puncte forte și slabe
- WriterAgent: transformă analize în text clar, profesional, pentru audiență de business

Sarcina primită: analizează competitorii principali ai unei firme de contabilitate din Cluj cu focus pe servicii digitale.

Procesul tău:
1. Trimite ResearcherAgent-ului o cerere specifică de cercetare
2. Trimite output-ul cercetării la AnalystAgent cu întrebările de analiză
3. Trimite analiza la WriterAgent cu instrucțiunile de formatare
4. Sintetizează output-ul final și prezintă-l structurat

Comunică cu fiecare worker prin mesaje clare cu formatul: [WORKER_NAME] TASK: [descrierea sarcinii] FORMAT_OUTPUT: [formatul așteptat]
```

## Prompting-ul workerilor

Workerii trebuie să aibă prompt-uri foarte specifice, cu output format standardizat. Aceasta este esențială pentru că output-ul lor devine input pentru alt agent.

```
Ești ResearcherAgent, un agent specializat în cercetare. Rolul tău:
- Primești o sarcină de cercetare de la orchestrator
- Returnezi NUMAI date brute structurate, fără interpretare sau recomandări
- Marchezi întotdeauna nivelul de încredere: [VERIFICAT] sau [NECESITA_VERIFICARE]
- Dacă nu găsești o informație, returnezi null pentru acel câmp, nu inventa date

Format obligatoriu de output:
{
  "task": "sarcina primită",
  "findings": [{"fact": "...", "source": "...", "confidence": "high/medium/low"}],
  "gaps": ["informații căutate dar negăsite"]
}
```

Al doilea exemplu — worker de scriere:

```
Ești WriterAgent, specializat în redactarea de conținut profesional de business. Primești:
- O analiză structurată cu date și concluzii
- Instrucțiuni de format și audiență

Regulile tale:
- Scrie NUMAI pe baza datelor primite, nu adăuga informații proprii
- Dacă datele sunt insuficiente pentru o secțiune, marchează cu [DATE INSUFICIENTE]
- Respectă exact lungimea și formatul specificat
- Ton: profesional, bazat pe date, fără clișee corporatiste
```

## Standardizarea comunicării între agenți

Una dintre cele mai frecvente cauze de eșec în sistemele multi-agent este lipsa unui format standardizat de comunicare. Dacă ResearcherAgent returnează text liber și AnalystAgent se așteaptă la JSON, pipeline-ul se rupe.

Bune practici pentru formatul inter-agent:
- Definește schema de output pentru fiecare worker în promptul lui
- Folosește format JSON sau Markdown structurat — nu text liber
- Include un câmp `status` (success/partial/failed) în fiecare output
- Include un câmp `confidence` sau `completeness` unde este relevant

## Gestionarea erorilor în pipeline

Un pipeline robust trebuie să gestioneze eșecuri. Ce se întâmplă dacă un worker returnează date incomplete sau eronatorii?

```
Ești orchestratorul pipeline-ului. Regulile de gestionare a erorilor:
1. Dacă un worker returnează status: "failed", reîncercă o singură dată cu instrucțiuni mai specifice
2. Dacă a doua încercare eșuează, continuă pipeline-ul și marchează secțiunea ca [DATE_LIPSĂ] în outputul final
3. Nu opri întregul pipeline din cauza eșecului unui singur worker
4. Raportează la final toate secțiunile cu date lipsă și motivul
```

## Exercițiu practic: designul unui pipeline

Aceasta este o lecție de tip exercițiu. Sarcina ta:

**Designează un pipeline multi-agent** pentru una din situațiile de mai jos (la alegere):

**Opțiunea A — Content creation pipeline:** Primește o temă și produce un articol de blog complet cu cercetare, structurare, scriere și optimizare SEO.

**Opțiunea B — Due diligence pipeline:** Primește numele unei companii și produce un raport de evaluare cu cercetare financiară, analiză competitivă și evaluare de riscuri.

**Opțiunea C — Customer support pipeline:** Primește un ticket de suport și determină categoria, prioritatea, răspunsul sugerat și dacă necesită escaladare umană.

Pentru fiecare opțiune, documentează:
1. Câți agenți și ce rol are fiecare
2. Tipul de pipeline (secvențial/paralel/ierarhic)
3. Promptul orchestratorului (minim 100 cuvinte)
4. Promptul a cel puțin unui worker (minim 50 cuvinte)
5. Formatul de comunicare între agenți

Nu există un răspuns corect unic — există design-uri mai robuste și mai puțin robuste. Evaluează-ți soluția după: claritatea rolurilor, standardizarea formatelor și gestionarea cazurilor de eroare.

## Provocări și limitări reale

**Costul:** Fiecare agent consumă tokens. Un pipeline cu 5 agenți poate costa de 5-10 ori mai mult decât un singur prompt.

**Latența:** Pași secvențiali înseamnă timpi de așteptare adunați. Un pipeline de 5 pași poate dura 30-60 de secunde.

**Propagarea erorilor:** O eroare la pasul 2 poate invalida tot ce urmează, dacă nu există logică de gestionare a erorilor.

**Complexitatea de debug:** Când ceva merge greșit, nu este întotdeauna clar care agent a eșuat și de ce.

**Soluția generală:** Începe simplu — cu 2-3 agenți bine definiți — și adaugă complexitate doar când beneficiile sunt clare.

## Concluzie

Sistemele multi-agent reprezintă un salt important în modul în care gândim utilizarea AI pentru sarcini complexe. În loc să ceri unui singur model să facă totul, împarți sarcina în componente specializate, fiecare optimizată pentru ce face cel mai bine. Cheia succesului nu este numărul de agenți, ci calitatea designului: roluri clare, formate standardizate de comunicare și logică robustă de gestionare a erorilor. Aceste principii, aplicate consistent, transformă un colaj de prompts în un sistem coordonat capabil să producă output de calitate profesională.
