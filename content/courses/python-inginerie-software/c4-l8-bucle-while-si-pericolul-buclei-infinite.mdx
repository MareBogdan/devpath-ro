# Bucle WHILE și pericolul buclei infinite

## HOOK

Un agent AI conversațional trebuie să continue să "gândească" — să apeleze unelte, să evalueze rezultate, să decidă pasul următor — **până** ajunge la un răspuns final, nu de un număr fix de ori cunoscut dinainte. Un `for` din L7 nu se pretează aici: nu știi de la început câte iterații va avea nevoie agentul. Ai nevoie de o buclă care continuă **cât timp** o condiție rămâne adevărată, indiferent câte iterații durează asta — exact rolul lui `while`.

Dar aceeași flexibilitate care face `while` puternic e și cea mai frecventă sursă de bug-uri catastrofale pentru începători: dacă condiția nu devine niciodată falsă, bucla rulează la infinit, blocând programul complet — sau, mai rău, într-un serviciu de producție, consumând CPU la 100% până se prăbușește întregul server.

---

## CONTEXT

Bucla `while` e conceptual identică în aproape toate limbajele de programare — o verificare de condiție înaintea fiecărei iterații, repetată câtă vreme condiția rămâne adevărată. Diferența dintre `for` și `while` nu e de putere expresivă (orice `for` poate fi rescris ca `while`, și invers, cu efort) — e de **claritate a intenției**: `for` comunică "știu peste ce iterez", `while` comunică "continui până se schimbă o condiție externă, nu știu exact câte pași".

Bucla infinită necontrolată e una dintre cele mai vechi și mai temute clase de bug din istoria programării — motivul pentru care problema oprii (*halting problem*), demonstrată de Alan Turing în 1936, arată că e matematic **imposibil** să construiești un algoritm general care să determine, pentru orice program arbitrar, dacă acesta se va termina vreodată sau va rula la infinit.

## MIEZUL

### Forma de bază

```python
contor = 0
while contor < 5:
    print(contor)
    contor += 1     # ESENȚIAL — fără asta, condiția nu se schimbă niciodată
# 0, 1, 2, 3, 4
```

Condiția e verificată **înainte** de fiecare iterație, inclusiv prima — dacă `contor` ar începe deja la `5`, bucla nu s-ar executa deloc, nici o singură dată. Fiecare iterație trebuie să facă *ceva* care mișcă starea programului mai apropiat de momentul în care condiția devine falsă — omiterea acestui pas (uitarea lui `contor += 1`) produce direct o buclă infinită.

<CosmoHint emotion="sad">
`while True:` fără niciun `break` în interior e cea mai directă rețetă pentru un program blocat, care nu va răspunde niciodată la nimic — trebuie forțat să se închidă manual (Ctrl+C în terminal, sau kill de proces). Într-un server de producție, o buclă infinită accidentală într-o cerere HTTP poate ocupa un worker întreg la nesfârșit, refuzând să răspundă vreodată — și, la cerințe repetate similare, poate consuma toți worker-ii disponibili, blocând întregul serviciu pentru toți utilizatorii. Verifică ÎNTOTDEAUNA, înainte de a rula cod cu `while`, că există o cale clară către terminare.
</CosmoHint>

### Pattern-uri sigure — `while True` + `break` condiționat

Contraintuitiv, `while True:` combinat cu `break` explicit e des mai clar decât o condiție complexă în antetul buclei, mai ales când decizia de oprire depinde de logică evaluată *în interiorul* buclei:

```python
while True:
    raspuns = input("Introduceți un număr pozitiv (sau 'stop'): ")
    if raspuns == "stop":
        break
    numar = int(raspuns)
    if numar > 0:
        print(f"Ai introdus: {numar}")
        break
    print("Numărul trebuie să fie pozitiv, încearcă din nou.")
```

Aici, condiția de oprire depinde de input-ul utilizatorului, evaluat *în timpul* iterației — mult mai natural cu `break` decât cu o precondiție complicată calculată înainte de a intra în buclă.

### `while` pentru un agent AI — cazul de uz real

```python
def ruleaza_agent(intrebare, max_pasi=10):
    context = [intrebare]
    pas = 0

    while pas < max_pasi:
        raspuns_model = apeleaza_model(context)

        if raspuns_model.este_final:
            return raspuns_model.continut

        rezultat_unealta = executa_unealta(raspuns_model.unealta_ceruta)
        context.append(rezultat_unealta)
        pas += 1

    return "Am atins limita de pași fără un răspuns final."
```

Acest pattern — `while` cu o **limită maximă de siguranță** (`max_pasi`), nu doar o condiție de terminare "naturală" — e esențial pentru orice logică de agent AI care poate, teoretic, să bucleze fără să convergă niciodată către un răspuns final. Fără `max_pasi`, un model care nu produce niciodată `este_final=True` (din cauza unui prompt prost, unei unelte defectuoase, sau pur și simplu a limitelor modelului) ar bloca execuția la infinit.

| Situație | Alegere recomandată |
|---|---|
| Număr de iterații cunoscut dinainte | `for` (L7) |
| Repetiție "până se schimbă o condiție externă" | `while conditie:` |
| Logică de oprire complexă, evaluată în interior | `while True:` + `break` condiționat |
| Orice buclă care ar putea, teoretic, să nu se termine | Adaugă mereu o limită maximă de siguranță |

### Cum apar buclele infinite accidentale — trei cauze comune

**Uitarea incrementării/modificării variabilei de control**: `contor < 5`, dar linia `contor += 1` a fost ștearsă accidental sau plasată greșit în afara buclei.

**Modificarea greșită a direcției**: `while contor > 0: contor += 1` — condiția verifică descreșterea, dar codul incrementează, nu decrementează. Condiția rămâne mereu adevărată.

**Condiție bazată pe stare externă care nu se actualizează niciodată**: `while not fisier_gata(): pass` — dacă `fisier_gata()` verifică o condiție care nu se va schimba niciodată fără intervenție separată (alt proces, alt thread), bucla rulează la infinit, consumând 100% CPU fără să facă nimic util — un pattern numit **busy waiting**, considerat antipattern exact din acest motiv (soluția corectă e de obicei un mecanism de așteptare eficientă, nu o buclă goală care verifică repetat).

<CosmoHint emotion="encouraging">
`Ctrl+C` în terminal trimite un semnal `SIGINT` procesului activ — cea mai rapidă metodă de a întrerupe manual o buclă infinită accidentală în timpul dezvoltării. Dacă un script Python rămâne "blocat" fără niciun output vizibil, primul instinct util e să verifici dacă vreo condiție de `while` din codul recent scris nu se actualizează corect — cauza numărul unu a acestui simptom pentru cineva care abia învață bucle.
</CosmoHint>

### Debugging practic — instrumentarea unei bucle suspecte

Când o buclă `while` nu se termină cum te-ai aștepta, cea mai rapidă tehnică de diagnosticare e să afișezi starea relevantă la fiecare iterație, temporar, doar pentru debugging:

```python
contor = 0
while contor < 5:
    print(f"DEBUG: contor = {contor}")   # temporar, se șterge după debugging
    # ... restul logicii ...
    contor += 1
```

Dacă output-ul arată `contor` blocat la aceeași valoare, repetată la infinit, ai găsit imediat cauza — variabila de control nu se modifică undeva unde te-ai aștepta. Această tehnică simplă rezolvă rapid marea majoritate a buclelor infinite accidentale din cod de începător.

### `while`/`else` — clauza rar folosită, dar simetrică cu `for`/`else`

Exact ca bucla `for` din L7, `while` are propria clauză `else`, care se execută doar dacă bucla s-a terminat **normal**, prin condiția devenită falsă, nu printr-un `break`:

```python
tentative = 0
maxim_tentative = 3

while tentative < maxim_tentative:
    raspuns = input("Ghicește numărul: ")
    if raspuns == "42":
        print("Corect!")
        break
    tentative += 1
else:
    print("Ai epuizat toate tentativele.")   # se execută DOAR dacă nu a fost 'break'
```

Pattern-ul aici e identic conceptual cu cel de la `for`/`else`: `else` comunică "bucla a rulat complet, fără să fi fost interceptată de un `break`" — util pentru a distinge explicit între "am găsit ce căutam și am ieșit prematur" și "am parcurs toată logica, fără succes." Rar folosit în practică (mulți dezvoltatori Python experimentați evită deliberat structura, considerând-o confuză la prima citire), dar util de recunoscut citind cod scris de alții.

### Bucle `while` cu multiple condiții de oprire

O buclă `while` reală, de producție, verifică rareori o singură condiție simplă — de obicei combină mai multe motive posibile de oprire, folosind exact operatorii logici din L5:

```python
timp_scurs = 0
raspuns_primit = False
eroare_critica = False

while timp_scurs < 30 and not raspuns_primit and not eroare_critica:
    raspuns_primit, eroare_critica = verifica_status()
    timp_scurs += 1

if eroare_critica:
    print("Operațiune întreruptă din cauza unei erori.")
elif raspuns_primit:
    print("Răspuns primit cu succes.")
else:
    print("Timeout — nicio confirmare în 30 de unități de timp.")
```

Acest pattern combină trei tipuri de condiții de oprire, oricare dintre ele suficientă pentru a termina bucla — un timeout (protecție de siguranță de bază), succesul cazului normal, și un eșec explicit care nu trebuie ignorat. Structura `if`/`elif`/`else` de după buclă distinge apoi *care* dintre condiții a declanșat efectiv ieșirea, informație pe care simpla terminare a buclei n-o comunică singură.

### Comparație directă cu recursivitatea — o alternativă la `while`

Anumite probleme rezolvate natural cu `while` (repetă până se atinge o condiție) au și o formulare recursivă echivalentă — o funcție care se apelează pe sine, cu parametri modificați, până ajunge la un caz de bază:

```python
def numara_descrescator_while(n):
    while n > 0:
        print(n)
        n -= 1

def numara_descrescator_recursiv(n):
    if n <= 0:            # caz de bază — oprește recursivitatea
        return
    print(n)
    numara_descrescator_recursiv(n - 1)   # apel recursiv, cu parametru modificat
```

Python limitează adâncimea maximă de recursivitate (implicit ~1000 de apeluri imbricate, configurabil prin `sys.setrecursionlimit()`) — o buclă `while` echivalentă nu are această limitare, motiv pentru care recursivitatea, oricât de elegantă sintactic pentru anumite probleme (parcurgerea unor structuri arborescente, de exemplu), devine impracticabilă pentru un număr foarte mare de repetări, unde `while`/`for` rămân opțiunea sigură.

Depășirea limitei de recursivitate produce `RecursionError: maximum recursion depth exceeded` — un semnal explicit, ușor de diagnosticat, spre deosebire de o buclă `while` infinită, care nu aruncă nicio eroare, doar rulează la nesfârșit fără să spună nimic. Această diferență de comportament la eșec e un argument practic suplimentar pentru `while` cu o limită de siguranță explicită (`max_pasi`, discutat deja la agentul AI): preferi un eșec clar, rapid, diagnosticabil, în locul unei tăceri infinite care blochează întregul program fără indiciu.

### Polling cu `while` — verificare repetată a unei stări externe

Un pattern practic frecvent, legat direct de conceptele din C3: verificarea repetată a stării unei operațiuni asincrone care rulează în altă parte — un job de antrenare pe un server remote, o cerere de procesare video care durează minute:

```python
import time

def asteapta_finalizarea(id_job, timeout_secunde=300, interval_verificare=5):
    timp_scurs = 0
    while timp_scurs < timeout_secunde:
        status = verifica_status_job(id_job)
        if status == "finalizat":
            return status
        if status == "eroare":
            raise RuntimeError(f"Job-ul {id_job} a eșuat")
        time.sleep(interval_verificare)     # pauză, nu verifici la nesfârșit, agresiv, fără pauză
        timp_scurs += interval_verificare
    raise TimeoutError(f"Job-ul {id_job} nu s-a finalizat în {timeout_secunde}s")
```

Acest cod combină exact elementele discutate: o limită de timeout explicită (protecție contra buclei infinite), o pauză între verificări (`time.sleep()`, evitând busy waiting-ul deja menționat ca antipattern), și gestionare explicită a celor trei rezultate posibile — succes, eroare, sau epuizarea timpului alocat. E structura de bază a oricărui client care așteaptă finalizarea unei operațiuni lungi, întâlnită constant în integrări cu servicii AI care procesează cereri asincron.

Alegerea intervalului de verificare (`interval_verificare`) e un compromis practic constant: prea scurt, generezi trafic inutil de rețea, apropiat de un polling risipitor (revezi discuția din C3 despre polling vs. webhooks); prea lung, întârzii inutil detectarea finalizării reale. Un interval de câteva secunde e tipic suficient pentru majoritatea operațiunilor de durată medie, dar valoarea corectă depinde direct de cât timp durează efectiv operațiunea monitorizată.

## REVEAL

{/* TABLE */}

| Semnal | Cauză probabilă |
|---|---|
| Programul "îngheață", niciun output nou | Buclă infinită, probabil `while` |
| CPU la 100% fără progres vizibil | Busy waiting sau buclă infinită fără `sleep`/pauză |
| Variabila de control afișată identic la fiecare iterație (debugging) | Lipsa actualizării ei în interiorul buclei |
| Agent AI care nu se oprește niciodată | Lipsa unei limite maxime de pași (`max_pasi`) |

<FactBox>
**Bucle WHILE în cifre:**
- Problema opririi (Alan Turing, 1936): demonstrează matematic imposibilitatea unui detector universal de bucle infinite
- `while True:` + `break`: pattern comun, sigur DOAR cu o cale clară de terminare garantată
- Busy waiting: antipattern — consumă 100% dintr-un core CPU fără progres util
- `Ctrl+C`: trimite `SIGINT`, metoda standard de întrerupere manuală a unui proces blocat
- Orice agent AI cu buclă `while` de raționament: necesită obligatoriu o limită maximă de pași
- Bucla infinită într-un server de producție: poate bloca un worker/thread la nesfârșit, afectând disponibilitatea întregului serviciu
</FactBox>

## ÎNCHEIERE

`while` completează `for`: unde `for` iterează peste o colecție cunoscută, `while` continuă câtă vreme o condiție rămâne adevărată, indiferent cât durează asta. Puterea suplimentară vine cu un risc real — bucla infinită — pe care orice cod de producție, mai ales logica de agent AI, trebuie să-l elimine explicit printr-o limită maximă de siguranță.

Ai scris deja mici blocuri de logică repetate în buclă. Următorul pas natural e să le împachetezi în unități reutilizabile, apelabile din multiple locuri, cu propriile parametri și rezultate — subiectul lecției următoare: funcțiile.
