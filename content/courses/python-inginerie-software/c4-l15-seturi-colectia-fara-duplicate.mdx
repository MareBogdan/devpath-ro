# Set-uri: Colecția fără duplicate

## HOOK

Un dataset de antrenare are 50.000 de exemple, dar mulți utilizatori au trimis accidental duplicate — același text, salvat de două-trei ori. Vrei rapid lista de valori **unice**. Cu o listă, ai scrie manual o buclă care verifică, pentru fiecare element nou, dacă a mai apărut deja — `O(n²)` în cel mai simplu caz, dureros de lent la scară.

```python
unic = list(set(lista_cu_duplicate))
```

O singură linie. **Set-ul** garantează structural că fiecare valoare apare o singură dată — nu prin verificare manuală repetată, ci prin design: aceeași structură de hash care oferă dicționarelor acces `O(1)` din L13 elimină automat duplicatele, pentru că insera aceeași valoare de două ori nu are niciun efect vizibil — set-ul o "vede" deja acolo.

---

## CONTEXT

Setul matematic — o colecție de elemente distincte, fără ordine intrinsecă, cu operații bine definite de reuniune, intersecție, diferență — are secole de teorie formală în spate (teoria mulțimilor, Georg Cantor, secolul XIX). Python implementează direct această structură ca tip nativ, `set`, susținut intern de exact același mecanism de hashing folosit pentru dicționare (L13) — motiv pentru care set-urile au aceleași restricții de conținut (doar elemente imutabile/hashabile) și aceleași garanții de performanță.

## MIEZUL

### Creare și operații de bază

```python
fructe = {"măr", "pară", "kiwi", "măr"}    # "măr" apare o dată în rezultat, duplicatul e ignorat
print(fructe)                                   # {'kiwi', 'măr', 'pară'} — ORDINEA nu e garantată

fructe.add("banană")           # adaugă un element
fructe.discard("kiwi")           # elimină, FĂRĂ eroare dacă nu exista
fructe.remove("pară")             # elimină, ARUNCĂ KeyError dacă nu exista

print("măr" in fructe)             # True — verificare O(1), la fel ca la dicționare
```

Un set gol **nu** se scrie `{}` — acea sintaxă creează un dicționar gol (o ambiguitate istorică a limbajului). Un set gol se scrie explicit `set()`.

<CosmoHint emotion="thinking">
De ce set-urile nu au ordine garantată, spre deosebire de liste și (din Python 3.7) dicționare? Pentru că un set nu ține evidența pozițiilor de inserare deloc — stochează elementele exclusiv pe baza hash-ului lor, în structuri interne optimizate pentru căutare rapidă, nu pentru păstrarea secvenței. Dacă ai nevoie de ordine, un set e structural nepotrivit — foloseşte o listă (cu deduplicare manuală, dacă e nevoie) sau `dict.fromkeys()`, care păstrează ordinea de inserare eliminând duplicatele.
</CosmoHint>

### Operațiile matematice de set — reuniune, intersecție, diferență

{/* TABLE */}

| Operație | Simbol | Metodă | Rezultat |
|---|---|---|---|
| Reuniune | `\|` | `.union()` | Toate elementele din ambele set-uri |
| Intersecție | `&` | `.intersection()` | Doar elementele comune ambelor |
| Diferență | `-` | `.difference()` | Elemente din primul, dar NU din al doilea |
| Diferență simetrică | `^` | `.symmetric_difference()` | Elemente în EXACT unul dintre set-uri, nu ambele |
| Subset | `<=` | `.issubset()` | Toate elementele primului sunt și în al doilea |

```python
grupa_a = {"Ana", "Ion", "Maria"}
grupa_b = {"Ion", "Radu", "Elena"}

print(grupa_a | grupa_b)   # {'Ana', 'Ion', 'Maria', 'Radu', 'Elena'} — reuniune
print(grupa_a & grupa_b)    # {'Ion'} — intersecție (comuni)
print(grupa_a - grupa_b)     # {'Ana', 'Maria'} — doar în A
print(grupa_a ^ grupa_b)      # {'Ana', 'Maria', 'Radu', 'Elena'} — în exact una din grupe
```

Aceste operații sunt implementate direct, optimizate intern, mult mai rapide și mai clare decât rescrierea manuală cu bucle și `if`-uri asupra listelor: "cine e în ambele echipe" (`&`), "cine e doar în prima" (`-`), "cine s-a schimbat de la o versiune la alta a listei" (`^`).

### Cazul de uz canonic — deduplicare rapidă

```python
raspunsuri_utilizatori = ["da", "nu", "da", "poate", "da", "nu"]
raspunsuri_unice = set(raspunsuri_utilizatori)
print(raspunsuri_unice)          # {'da', 'nu', 'poate'}
print(len(raspunsuri_unice))       # 3 — numărul de valori DISTINCTE

# Verificare rapidă de apartenență la o listă mare de cuvinte interzise:
cuvinte_interzise = {"spam", "reclama", "escrocherie"}   # SET, nu listă — pentru viteză

def contine_cuvant_interzis(text):
    cuvinte_text = set(text.lower().split())
    return bool(cuvinte_text & cuvinte_interzise)   # intersecție ne-vidă = există potrivire
```

Ultimul exemplu arată un pattern practic important pentru performanță: dacă vei verifica repetat apartenența unui element la o colecție fixă (o listă de cuvinte interzise, o listă de ID-uri permise), convertirea ei la `set` **o singură dată**, la început, transformă fiecare verificare ulterioară din `O(n)` (căutare secvențială într-o listă) în `O(1)` — o optimizare simplă, dar cu impact real la colecții mari, verificate frecvent.

### `frozenset` — versiunea imutabilă

```python
permis = frozenset({"citire", "scriere"})   # imutabil — nu poate fi modificat după creare

configurari = {permis: "acces standard"}    # POATE fi cheie de dicționar, spre deosebire de set normal
```

Exact ca relația listă↔tuple din L14, `set`↔`frozenset` urmează același model: versiunea mutabilă nu poate fi cheie de dicționar sau element al altui set (nu e hashabilă); versiunea imutabilă, da. Rar folosit în cod de zi cu zi, dar util de recunoscut când apare în biblioteci care au nevoie de colecții de valori unice, imutabile, ca și configurări fixe.

<CosmoHint emotion="encouraging">
Elementele unice dintr-un vocabular de tokeni (folosit la tokenizarea textului pentru modele de limbaj) sunt, conceptual, exact un set — fiecare token distinct apare o singură dată în vocabular, indiferent de câte ori apare în textul original de antrenare. `set(text.split())` e o aproximare simplistă, dar corectă conceptual, a primului pas dintr-un pipeline real de construire a unui vocabular.
</CosmoHint>

### Set comprehensions — construcție concisă, revizitată în context

Exact ca la liste (L18) și dicționare (L13), set-urile au propria formă de comprehension, cu sintaxa aproape identică, doar cu acolade în loc de paranteze pătrate:

```python
numere = [1, 2, 2, 3, 3, 3, 4]
patrate_unice = {n ** 2 for n in numere}   # {16, 1, 4, 9} — duplicatele din 'numere' nu contează

cuvinte = ["Python", "python", "PYTHON", "java"]
cuvinte_normalizate = {c.lower() for c in cuvinte}   # {'python', 'java'} — normalizare + deduplicare
```

Al doilea exemplu combină transformarea (normalizarea la litere mici) cu deduplicarea automată, într-o singură expresie — util constant pentru curățarea de date de intrare unde aceeași valoare logică poate apărea în variante ușor diferite de formatare (majuscule/minuscule, spații suplimentare).

### Operatori de actualizare in-place — `|=`, `&=`, `-=`

Exact ca operatorii aritmetici compuși din L5, operațiile de set au echivalente care modifică setul existent direct, în loc să creeze unul nou:

```python
permise = {"citire", "scriere"}
permise |= {"executare"}          # echivalent cu .update() — adaugă elemente, ÎN LOC
print(permise)                       # {'citire', 'scriere', 'executare'}

permise &= {"citire", "executare"}    # păstrează DOAR intersecția, ÎN LOC
print(permise)                          # {'citire', 'executare'}
```

`|=` (reuniune in-place, echivalent cu `.update()`), `&=` (intersecție in-place, echivalent cu `.intersection_update()`), `-=` (diferență in-place) — toate modifică setul existent direct, spre deosebire de `|`, `&`, `-` obișnuiți, care creează întotdeauna un set nou, lăsând operanzii originali neschimbați. Aceeași distincție filozofică repetată constant în acest curs: operator care creează vs. operator/metodă care modifică în loc.

### Complexitatea operațiilor de set — de ce sunt eficiente la scară

{/* TABLE */}

| Operație | Complexitate tipică |
|---|---|
| `x in set_a` | O(1) |
| `set_a.add(x)` | O(1) amortizat |
| `set_a \| set_b` (reuniune) | O(len(a) + len(b)) |
| `set_a & set_b` (intersecție) | O(min(len(a), len(b))) |
| `set_a - set_b` (diferență) | O(len(a)) |

Fiecare operație de set rămâne liniară sau mai bună în raport cu dimensiunea totală implicată — niciodată pătratică, spre deosebire de echivalentele naive scrise manual cu bucle imbricate peste liste (verifică fiecare element din `a` împotriva fiecărui element din `b`, o operațiune O(n×m)). Această diferență de complexitate explică de ce conversia explicită la `set`, chiar și temporară, doar pentru o singură verificare de apartenență repetată, merită costul inițial de conversie la colecții suficient de mari.

### Găsirea elementelor duplicate — un caz de uz derivat

Deși set-urile elimină duplicatele prin design, găsirea explicită a *căror* elemente sunt duplicate (nu doar eliminarea lor) e un caz de uz separat, care combină un set cu o buclă simplă:

```python
def gaseste_duplicate(lista):
    vazute = set()
    duplicate = set()
    for element in lista:
        if element in vazute:
            duplicate.add(element)
        else:
            vazute.add(element)
    return duplicate

print(gaseste_duplicate([1, 2, 3, 2, 4, 1, 5]))   # {1, 2}
```

Acest pattern — un set `vazute` care acumulează progresiv elementele întâlnite deja, verificat la fiecare pas — e o tehnică generală extrem de utilă, aplicabilă oricărei probleme care cere "am mai văzut asta înainte?" într-o singură parcurgere a datelor, cu complexitate O(n) totală, față de O(n²) pentru o soluție naivă care ar compara fiecare element cu toate celelalte.

### Set-uri și tipuri numerice — comparație de egalitate, nu de identitate

```python
a = {1, 2.0, True}   # 1 == 1.0 == True numeric, deci setul reține UN SINGUR element
print(a)                # {1} sau {True} — reprezentarea variază, dar setul conține un singur element
print(len(a))              # 1
```

Set-urile determină unicitatea prin egalitate de valoare (`==`), combinată cu hash-ul obiectului — nu prin identitate (`is`). Pentru că `1`, `1.0`, și `True` sunt egale numeric între ele (revezi L4, unde `bool` e subclasă de `int`) și au același hash, un set le tratează ca "aceeași" valoare, păstrând doar prima întâlnită — un detaliu de comportament surprinzător prima dată când apare accidental într-un cod care amestecă tipuri numerice diferite, presupunând implicit că sunt distincte.

Această regulă generală — orice două obiecte egale (`==`) TREBUIE să aibă același hash, o cerință impusă de proiectarea corectă a oricărei clase custom care implementează atât `__eq__` cât și `__hash__` — nu e specifică set-urilor, ci se aplică identic dicționarelor: dacă ai scrie vreodată o clasă proprie destinată să fie folosită ca element de set sau cheie de dicționar, respectarea acestei corespondențe e obligatorie pentru un comportament corect, altfel riști exact bug-uri similare celui ilustrat aici cu tipurile numerice amestecate.

### Set-uri ca filtru rapid pentru liste mari

```python
id_uri_permise = {101, 205, 340, 512, 890}   # set, pentru verificare rapidă de apartenență

toate_comenzile = obtine_toate_comenzile()   # listă potențial mare, mii de înregistrări
comenzi_relevante = [c for c in toate_comenzile if c.id_utilizator in id_uri_permise]
```

Combinația set + list comprehension e pattern-ul standard pentru filtrarea eficientă a unei colecții mari după apartenența la o listă de valori permise — verificarea `in` pe setul `id_uri_permise` rămâne O(1) la fiecare element din `toate_comenzile`, indiferent cât de mare devine acea listă de valori permise, spre deosebire de o listă folosită direct ca filtru, unde fiecare verificare `in` ar costa O(m), cu m dimensiunea listei de valori permise.

Diferența de performanță crește direct proporțional cu dimensiunea ambelor colecții implicate: pentru o listă de 10.000 de comenzi filtrate față de 5.000 de ID-uri permise, varianta cu listă ca filtru ar face potențial 50 de milioane de comparații (10.000 × 5.000), în timp ce varianta cu set rămâne la aproximativ 10.000 de verificări O(1) — o diferență de câteva ordine de mărime, vizibilă direct în timpul real de execuție.

### Set-uri disjuncte — verificarea rapidă a absenței oricărei suprapuneri

```python
grupa_a = {"Ana", "Ion"}
grupa_b = {"Maria", "Radu"}

print(grupa_a.isdisjoint(grupa_b))   # True — nicio suprapunere
print(grupa_a.isdisjoint({"Ion", "Elena"}))   # False — 'Ion' apare în ambele
```

`.isdisjoint()` verifică rapid, O(min(len(a), len(b))), dacă două set-uri nu au niciun element în comun — mai eficient decât a calcula intersecția completă (`grupa_a & grupa_b`) doar pentru a verifica dacă rezultatul e gol, pentru că `.isdisjoint()` se oprește la prima potrivire găsită, fără să construiască întregul set de rezultate al intersecției.

De ce contează diferența dintre `.isdisjoint()` și calcularea intersecției complete, dacă amândouă îți spun "există suprapunere sau nu"? Pentru colecții mici, diferența e neglijabilă — dar la seturi cu mii sau milioane de elemente, `.isdisjoint()` poate opri verificarea la prima potrivire găsită, în timp ce intersecția completă construiește tot rezultatul înainte să-l poți verifica, chiar dacă tu ai nevoie doar de răspunsul boolean "da sau nu". ## REVEAL

{/* TABLE */}

| Structură | Ordonată | Duplicate permise | Mutabilă | Poate fi cheie/element în alt set |
|---|---|---|---|---|
| Listă | Da | Da | Da | Nu |
| Tuple | Da | Da | Nu | Da |
| Dicționar | Da (din 3.7) | Chei: nu; valori: da | Da | Nu |
| Set | Nu | **Nu** | Da | Nu |
| Frozenset | Nu | Nu | **Nu** | Da |

<FactBox>
**Set-uri în cifre:**
- Verificare apartenență (`in`): **O(1)**, identic cu dicționarele — aceeași structură de hash internă
- `{}` gol: creează un DICȚIONAR, nu un set — pentru set gol, folosește explicit `set()`
- Operații matematice native: reuniune, intersecție, diferență, diferență simetrică — toate O(n) sau mai rapide
- Elemente permise: doar tipuri imutabile/hashabile (string, int, tuple), la fel ca cheile de dicționar
- `frozenset`: versiunea imutabilă, poate fi folosită ca element al altui set sau cheie de dicționar
- Deduplicare listă: `list(set(lista))` — pattern extrem de comun, dar pierde ordinea originală
</FactBox>

## ÎNCHEIERE

Set-urile completează trioul de colecții fundamentale Python — liste pentru ordine cu duplicate, dicționare pentru acces prin cheie, set-uri pentru unicitate garantată cu verificare instant. Toate trei se sprijină pe două idei recurente: mutabilitate (și consecințele ei asupra referințelor partajate) și hashing (și restricțiile de conținut pe care le impune).

Ai văzut deja diferența mutabil/imutabil aplicată repetat — la string-uri (L4), liste vs. tuple-uri (L14), set vs. frozenset. Lecția următoare tratează acest concept direct, complet, ca subiect de sine stătător — de ce contează, cum se manifestă exact, și cum previi bug-urile clasice pe care le cauzează confuzia dintre ele.
