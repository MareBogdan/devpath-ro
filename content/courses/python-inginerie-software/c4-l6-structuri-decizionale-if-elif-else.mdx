# Structuri decizionale: If/Elif/Else

## HOOK

Un sistem de rate limiting dintr-o API (revezi C3 L22) trebuie să decidă, pentru fiecare cerere: e sub limită → procesează normal; e la limită dar cu grace period → procesează cu avertisment; a depășit limita → respinge cu `429`. Trei căi de execuție complet diferite, dintr-o singură decizie inițială — exact structura pe care `if`/`elif`/`else` o modelează direct în cod.

Fiecare program cu vreo formă de "comportament adaptiv" — de la un simplu formular de validare, până la logica unui agent AI care decide "răspund direct sau apelez o unealtă externă?" — se reduce, la nivelul lui cel mai granular, la o secvență de astfel de ramificări. Nu există magie mai profundă în spatele "deciziei" unui program — există doar condiții evaluate în ordine, prima care e adevărată câștigând execuția.

---

## CONTEXT

Structura `if`/`else` există, sub o formă sau alta, în aproape orice limbaj de programare de la Fortran (1957) încoace — e unul din cele trei elemente fundamentale ale programării structurate (alături de secvență și repetiție), teoretizate formal prin **teorema Böhm-Jacopini** (1966), care demonstrează că orice program calculabil poate fi construit din exact aceste trei tipare de control.

Particularitatea Python — `elif` — e o contracție deliberată de "else if", introdusă pentru a evita indentarea tot mai adâncă pe care limbajele fără acest cuvânt-cheie (unele versiuni vechi de BASIC, de exemplu) o forțau la lanțuri lungi de condiții alternative.

## MIEZUL

### Forma de bază — `if`, opțional `elif`, opțional `else`

```python
varsta = 25

if varsta < 18:
    categorie = "minor"
elif varsta < 65:
    categorie = "adult"
else:
    categorie = "senior"

print(categorie)   # "adult"
```

Regulile de evaluare, esențiale de memorat: Python evaluează condițiile **în ordine**, de sus în jos. Prima condiție care e `True` execută blocul corespunzător, iar **toate celelalte ramuri sunt ignorate complet** — chiar dacă și ele ar fi tehnic adevărate. `else` (opțional) execută doar dacă niciuna dintre condițiile de mai sus n-a fost adevărată.

```python
x = 10
if x > 5:
    print("mare")
elif x > 0:
    print("pozitiv")     # NU se execută, chiar dacă x > 0 e adevărat —
                            # prima condiție (x > 5) a câștigat deja
```

<CosmoHint emotion="thinking">
De ce ordinea condițiilor `elif` contează structural, nu doar stilistic? Pentru că evaluarea se oprește la prima potrivire. Dacă ai `if x > 0: ... elif x > 10: ...`, a doua ramură e practic moartă — orice `x > 10` satisface deja `x > 0`, deci prima ramură câștigă mereu, indiferent cât de specifică e a doua condiție. Regula practică: ordonează condițiile de la cea mai *specifică* la cea mai *generală*, sau riști cod care "pare" corect dar nu execută niciodată căile pe care crezi că le acoperă.
</CosmoHint>

### Imbricarea condițiilor — și de ce devine ilizibilă rapid

```python
def clasifica_utilizator(varsta, este_activ, tara):
    if varsta >= 18:
        if este_activ:
            if tara == "RO":
                return "adult activ RO"
            else:
                return "adult activ non-RO"
        else:
            return "adult inactiv"
    else:
        return "minor"
```

Fiecare nivel de imbricare crește indentarea, iar cititorul trebuie să țină minte simultan toate condițiile părinte pentru a înțelege ce înseamnă un bloc adânc imbricat. Practica recomandată — cunoscută ca **early return** sau **guard clauses** — rescrie exact aceeași logică, plat, mult mai lizibil:

```python
def clasifica_utilizator(varsta, este_activ, tara):
    if varsta < 18:
        return "minor"
    if not este_activ:
        return "adult inactiv"
    if tara == "RO":
        return "adult activ RO"
    return "adult activ non-RO"
```

Fiecare condiție "elimină" un caz și se termină cu `return`, eliberând cititorul de nevoia de a urmări starea acumulată din nivele de imbricare — codul se citește de sus în jos, un caz eliminat pe rând, fără să ții minte contextul anterior.

{/* TABLE */}

| Stil | Avantaj | Dezavantaj |
|---|---|---|
| Imbricat (`if` în `if`) | Explicit despre relația logică între condiții | Devine ilizibil rapid peste 2-3 nivele |
| Early return / guard clauses | Plat, ușor de citit, fiecare caz izolat | Necesită funcție (return-ul întrerupe execuția) |
| `elif` în lanț | Compact pentru alternative exclusive multiple | Ordinea condițiilor e critică |

### Expresia condițională (ternar) — `if`/`else` ca expresie

Din L2, ai văzut că `if` are și o formă de **expresie**, nu doar de instrucțiune — utilă pentru atribuiri simple, unde un bloc întreg ar fi exagerat:

```python
status = "adult" if varsta >= 18 else "minor"

# Echivalent, dar mai verbos:
if varsta >= 18:
    status = "adult"
else:
    status = "minor"
```

Regula de bun-simț: forma ternară e potrivită pentru decizii **simple, dintr-o singură expresie** per ramură. Pentru logică mai complexă (mai mult de o linie per caz, sau mai mult de 2-3 alternative), `if`/`elif`/`else` obișnuit rămâne mai lizibil — ternarul imbricat (`a if x else b if y else c`) devine rapid criptic.

### Match statement — `switch` structurat, din Python 3.10

Python nu a avut, pentru mult timp, un echivalent direct al `switch`-ului din C/Java. **Python 3.10** (2021) a introdus `match`, mult mai puternic decât un simplu switch — face **pattern matching** structural, nu doar comparație de valori:

```python
def gestioneaza_comanda(comanda):
    match comanda:
        case "start":
            return "Pornire sistem"
        case "stop":
            return "Oprire sistem"
        case ["restart", intarziere]:       # potrivire pe STRUCTURĂ, nu doar valoare
            return f"Restart cu întârziere de {intarziere}s"
        case _:                                # caz implicit — echivalentul lui 'else'
            return "Comandă necunoscută"
```

`case _:` (underscore) e caracterul wildcard — se potrivește cu orice, echivalentul explicit al `else` de la finalul unui lanț `elif`. Deși util, `match` rămâne mai puțin folosit în practică decât `if`/`elif`/`else` clasic pentru cazurile simple — util să-l recunoști citind cod modern, dar nu esențial pentru majoritatea logicii de zi cu zi.

<CosmoHint emotion="encouraging">
Un pattern frecvent în cod AI real: verificarea tipului de răspuns primit de la o API de model — `if raspuns.get("eroare"): gestioneaza_eroare(...) elif raspuns.get("continut_partial"): continua_streaming(...) else: proceseaza_raspuns_final(...)`. Structura decizională simplă din această lecție e literalmente cum orice cod de integrare cu un LLM decide ce ramură de logică să execute pentru fiecare bucată de răspuns primită.
</CosmoHint>

### `match` cu pattern-uri de tip și destructurare — dincolo de simplul `switch`

Puterea reală a lui `match` (L2 a introdus doar forma de bază) devine vizibilă la potrivirea pe **structură**, nu doar pe valoare exactă — capacitate pe care niciun `switch` clasic din alte limbaje nu o oferă direct:

```python
def descrie_raspuns_api(raspuns):
    match raspuns:
        case {"status": "eroare", "cod": cod}:
            return f"Eroare cu codul {cod}"
        case {"status": "succes", "date": [primul, *restul]}:
            return f"Succes, primul element: {primul}, încă {len(restul)} rânduri"
        case {"status": "succes", "date": []}:
            return "Succes, dar fără date"
        case _:
            return "Format necunoscut"
```

Fiecare `case` descrie simultan **forma** pe care trebuie s-o aibă valoarea (un dicționar cu anumite chei, o listă cu cel puțin un element) și extrage direct sub-valorile relevante în variabile noi (`cod`, `primul`, `restul`) — o combinație de verificare structurală și tuple unpacking (L3, L14) într-o singură construcție. Acest stil de potrivire, împrumutat din limbaje funcționale (Haskell, Rust, Scala), simplifică vizibil cod care altfel ar necesita lanțuri de `if`/`isinstance()`/acces manual la câmpuri imbricate.

### Guard clauses în `match` — condiții suplimentare per caz

```python
def clasifica_scor(scor):
    match scor:
        case n if n >= 90:
            return "excelent"
        case n if n >= 70:
            return "bun"
        case n if n >= 50:
            return "satisfăcător"
        case _:
            return "insuficient"
```

Clauza `if` de după un pattern (numită *guard*) adaugă o condiție suplimentară care trebuie satisfăcută pentru ca acel `case` să se potrivească — util pentru intervale numerice sau condiții care nu se pot exprima direct doar prin forma structurală a valorii. Rezultatul se citește aproape identic cu un lanț `elif` echivalent, dar unele echipe preferă `match` pentru claritatea vizuală a alternativelor paralele, mai ales când numărul de cazuri crește peste 4-5 ramuri.

### Operatorii logici ca prescurtare pentru decizii simple

L5 a introdus deja short-circuit evaluation pentru `and`/`or` — merită revizitat aici, în contextul direct al deciziilor, pentru un pattern extrem de comun în cod Python idiomatic:

```python
# Variantă cu if explicit:
if utilizator.nume:
    nume_afisat = utilizator.nume
else:
    nume_afisat = "Anonim"

# Variantă echivalentă, mai concisă, folosind 'or':
nume_afisat = utilizator.nume or "Anonim"
```

Funcționează pentru că `or` returnează primul operand truthy găsit (revezi L5) — dacă `utilizator.nume` e un string ne-gol (truthy), `or` returnează exact acea valoare, fără să evalueze deloc partea dreaptă; dacă e gol sau `None` (falsy), returnează `"Anonim"`. Această prescurtare e potrivită *doar* pentru valori implicite simple, unde falsy înseamnă corect "lipsă" — nu e potrivită dacă `0` sau `""` ar fi o valoare validă, intenționată, pe care n-ai vrea s-o înlocuiești accidental cu valoarea implicită.

### Verificarea explicită a tipului înainte de o decizie — `isinstance()`

O decizie frecventă în cod care primește date din surse externe (JSON dintr-o API, revezi C3 L20-L22) e verificarea tipului înainte de a proceda, exact pattern-ul deja introdus la `bool` în L4:

```python
def proceseaza_valoare(valoare):
    if isinstance(valoare, str):
        return valoare.strip().lower()
    elif isinstance(valoare, (int, float)):     # tuple de tipuri — 'sau unul, sau altul'
        return round(valoare, 2)
    elif isinstance(valoare, list):
        return len(valoare)
    else:
        return None
```

`isinstance()` acceptă un al doilea argument fie ca tip unic, fie ca tuple de tipuri acceptate simultan — util când mai multe tipuri trebuie tratate identic (`int` și `float`, ambele numerice, tratate la fel în exemplul de mai sus). Această structură — decizie pe tip, nu pe valoare — apare constant în cod care validează sau normalizează date de formă necunoscută dinainte, exact scenariul pe care Pydantic (L24) îl automatizează complet, dar care rămâne util de înțeles manual pentru cazuri simple, ad-hoc.

Diferența dintre `isinstance()` și verificarea directă cu `type() == ...` merită reținută: `isinstance()` respectă moștenirea (o subclasă a tipului cerut se potrivește, la fel cum `True` s-a potrivit deja cu `int` în L4), în timp ce `type(x) == int` cere o egalitate exactă de tip, ignorând orice relație de moștenire. Practica idiomatică recomandă `isinstance()` aproape universal, exact pentru această flexibilitate suplimentară, fără cost practic.

### Decizii bazate pe excepții vs. decizii bazate pe `if` — EAFP revizitat

L11 introduce filosofia EAFP a Python (easier to ask forgiveness than permission) — merită menționată aici, ca alternativă reală la o structură decizională explicită pentru anumite cazuri:

```python
# Stil LBYL (look before you leap) — verifici explicit înainte:
if "cheie" in dictionar:
    valoare = dictionar["cheie"]
else:
    valoare = None

# Stil EAFP — încerci direct, gestionezi eșecul:
try:
    valoare = dictionar["cheie"]
except KeyError:
    valoare = None
```

Ambele produc rezultatul identic, dar comunitatea Python preferă în general EAFP pentru cazuri unde eșecul e rar și verificarea explicită ar dubla costul (verifici, apoi accesezi din nou) — o alegere de stil pe care o vei vedea justificată complet abia în L11, dar care merită menționată acum, ca a treia cale posibilă alături de `if`/`elif`/`else` obișnuit.

Alegerea între cele două stiluri nu e strict o chestiune de gust: dacă absența cheii e cazul comun, previzibil, frecvent (verifici sistematic dacă un utilizator opțional a completat un câmp), `if`/`else` explicit comunică mai clar intenția și evită costul de a construi și captura o excepție doar pentru un caz normal, nu excepțional. Dacă absența e rară, o anomalie neobișnuită, EAFP evită overhead-ul verificării repetate pentru un caz care aproape niciodată nu se întâmplă.

## REVEAL

{/* TABLE */}

| Situație | Structură recomandată |
|---|---|
| O singură condiție, o singură alternativă | `if`/`else` |
| Multiple alternative exclusive | `if`/`elif`/`elif`/`else` |
| Atribuire simplă condiționată | Expresie ternară (`a if cond else b`) |
| Multe condiții imbricate → cod greu de citit | Refactorizare la early return |
| Potrivire pe structură/tip de date (Python 3.10+) | `match`/`case` |

<FactBox>
**Structuri decizionale în cifre:**
- Teorema Böhm-Jacopini (1966): demonstrează că orice program se reduce la secvență, decizie, repetiție
- `elif`: contracție de "else if", evită indentare crescută la lanțuri lungi de alternative
- `match`/`case`: introdus în **Python 3.10** (octombrie 2021)
- Evaluare `if`/`elif`: se oprește la prima condiție `True`, ignoră restul necondiționat
- Prag practic recomandat pentru refactorizare (imbricare → early return): peste **2-3 nivele**
- `case _:`: wildcard, se potrivește necondiționat cu orice valoare rămasă
</FactBox>

## ÎNCHEIERE

`if`/`elif`/`else` transformă o condiție logică (rezultatul operatorilor din L5) într-o ramificare reală de execuție — programul alege, la runtime, ce cale de cod urmează. Regula de aur pentru cod lizibil: evită imbricarea profundă, preferă early return, și rezervă ternarul pentru decizii cu adevărat simple.

O singură decizie, executată o dată, e utilă — dar majoritatea programelor reale trebuie să repete aceeași logică de multe ori, pentru multe elemente diferite. Lecția următoare introduce prima structură de repetiție: bucla `for`.
