# Modulul requests: Conectezi Python la orice API

## HOOK

L1 a arătat trei linii care fac o cerere HTTP. E timpul să dezvoltăm complet acele trei linii — parametri de query, header-e de autentificare, gestionarea timeout-urilor, tratarea erorilor de rețea. `requests` (nu parte din biblioteca standard, dar instalată aproape universal) e biblioteca de facto pentru comunicarea HTTP din Python — orice integrare cu o API AI, orice webhook, orice scraping de date trece, la un moment dat, prin această bibliotecă sau un echivalent direct al ei.

Fiecare concept din C3 (metode HTTP, status code-uri, header-e, autentificare) devine aici cod concret, executabil — teoria protocolului transformată în apeluri reale de funcție.

---

## CONTEXT

Înainte de `requests` (Kenneth Reitz, 2011), interacțiunea HTTP din Python se făcea prin `urllib`, parte din biblioteca standard, dar cu o API notoriu de verboasă și greu de folosit corect — construirea manuală de cereri, gestionarea explicită de encoding, cod semnificativ mai lung pentru operațiuni triviale. `requests` a devenit rapid, prin simplitatea API-ului ei, una din cele mai descărcate biblioteci Python din întregul ecosistem — motto-ul oficial al proiectului, "HTTP for Humans," reflectă exact filosofia de lizibilitate discutată în L2.

## MIEZUL

### Cererile de bază — GET, POST, și restul metodelor din C3 L20

```python
import requests

raspuns = requests.get("https://api.exemplu.ro/utilizatori/42")
print(raspuns.status_code)     # 200 (revezi C3 L20)
print(raspuns.json())            # parsează automat body-ul JSON într-un dicționar Python

raspuns_post = requests.post(
    "https://api.exemplu.ro/utilizatori",
    json={"nume": "Ana", "email": "ana@exemplu.ro"}   # 'json=' serializeaza automat dicționarul
)
```

Fiecare metodă HTTP din C3 L20 are o funcție corespunzătoare: `requests.get()`, `.post()`, `.put()`, `.patch()`, `.delete()`. Parametrul `json=` face automat două lucruri: serializează dicționarul Python în text JSON și setează corect header-ul `Content-Type: application/json` — echivalentul manual ar necesita `json.dumps()` explicit plus setarea manuală a header-ului.

<CosmoHint emotion="thinking">
De ce `raspuns.json()` poate arunca o excepție, chiar dacă cererea a "reușit" (status 200)? `raspuns.json()` PARSEAZĂ body-ul ca JSON — dacă serverul răspunde cu HTML (o pagină de eroare, de exemplu, la o URL greșită care totuși dă 200 dintr-un motiv de configurare) sau text simplu, parsarea aruncă `json.JSONDecodeError`. Statusul HTTP și validitatea conținutului sunt garanții COMPLET SEPARATE — un `200 OK` confirmă doar că serverul a primit și procesat cererea, nu că body-ul e neapărat JSON valid sau conține datele așteptate.
</CosmoHint>

### Query parameters, header-e, autentificare

```python
raspuns = requests.get(
    "https://api.exemplu.ro/cautare",
    params={"query": "python", "limita": 10},    # devine ?query=python&limita=10 în URL
    headers={"Authorization": "Bearer sk-abc123..."},   # revezi autentificarea din C3 L22
    timeout=5    # secunde — OBLIGATORIU în cod de producție
)
```

`params=` construiește automat query string-ul, cu encoding corect al caracterelor speciale (spații, diacritice) — evitând erori de formatare manuală a URL-ului. `headers=` transmite orice header custom, cel mai frecvent folosit pentru autentificare (`Authorization: Bearer ...`, exact pattern-ul API key din C3 L22).

**`timeout=` e critic, aproape universal omis de începători, cu consecințe reale**: fără el, `requests` **așteaptă la infinit** un răspuns care poate să nu vină niciodată (server blocat, rețea căzută) — exact clasa de bug discutată la buclele infinite din L8, dar la nivel de rețea. Un `timeout=5` garantează că, după 5 secunde fără răspuns, cererea eșuează explicit cu o excepție, gestionabilă prin `try`/`except` (L11), în loc să blocheze programul indefinit.

{/* TABLE */}

| Parametru `requests.get/post(...)` | Rol |
|---|---|
| `params=` | Query string (`?cheie=valoare`) |
| `json=` | Body serializat automat ca JSON |
| `data=` | Body ca form-encoded (formulare HTML clasice) |
| `headers=` | Header-e HTTP custom (autentificare, content-type) |
| `timeout=` | Secunde de așteptare maximă — OBLIGATORIU în producție |
| `verify=` | Verificarea certificatului TLS (revezi C3 L17) — dezactivare NEsigură, doar în dev |

### Gestionarea erorilor — `raise_for_status()` și excepțiile specifice

```python
try:
    raspuns = requests.get("https://api.exemplu.ro/date", timeout=5)
    raspuns.raise_for_status()      # aruncă excepție dacă status e 4xx/5xx (revezi C3 L20)
    date = raspuns.json()
except requests.exceptions.Timeout:
    print("Cererea a expirat — serverul nu a răspuns la timp.")
except requests.exceptions.ConnectionError:
    print("Nu s-a putut stabili conexiunea — verifică rețeaua.")
except requests.exceptions.HTTPError as eroare:
    print(f"Serverul a răspuns cu eroare: {eroare}")
```

Fără `raise_for_status()`, o cerere care primește `404` sau `500` **nu** aruncă automat nicio excepție — `requests` consideră "succes" faptul că a primit *un* răspuns, indiferent de conținutul statusului. `raise_for_status()` verifică explicit statusul și ridică `HTTPError` dacă e din familia `4xx`/`5xx` — pattern obligatoriu pentru orice cod care nu poate ignora sigur o eroare de server.

### Sesiuni — reutilizarea conexiunii pentru mai multe cereri

```python
sesiune = requests.Session()
sesiune.headers.update({"Authorization": "Bearer sk-abc123..."})

raspuns1 = sesiune.get("https://api.exemplu.ro/utilizatori/1")
raspuns2 = sesiune.get("https://api.exemplu.ro/utilizatori/2")
```

`requests.Session()` reutilizează conexiunea TCP (și handshake-ul TLS, revezi C3 L6, L17) între cereri multiple către același server — evită overhead-ul de a reface handshake-ul complet la fiecare cerere individuală, exact ideea de conexiune persistentă (`keep-alive`) discutată în C3 L20. Header-ele setate pe sesiune (`sesiune.headers.update(...)`) se aplică automat tuturor cererilor ulterioare — util pentru autentificare, evitând repetarea aceluiași header la fiecare apel individual.

### Retry cu backoff — reziliență la eșecuri temporare

```python
import time

def cerere_cu_retry(url, max_tentative=3):
    for tentativa in range(max_tentative):
        try:
            raspuns = requests.get(url, timeout=5)
            raspuns.raise_for_status()
            return raspuns.json()
        except requests.exceptions.RequestException as eroare:
            if tentativa == max_tentative - 1:
                raise   # ultima tentativă eșuată — propagă excepția
            time.sleep(2 ** tentativa)   # backoff exponențial: 1s, 2s, 4s...
```

Acest pattern combină direct concepte deja văzute: bucla `for` (L7), `try`/`except` (L11), și backoff exponențial (menționat la rate limiting, C3 L22) — cod de producție real pentru apeluri API care trebuie să tolereze eșecuri temporare de rețea, exact scenariul din integrarea cu orice model AI unde conexiunile pot fluctua ocazional.

<CosmoHint emotion="encouraging">
Fiecare SDK oficial de model AI (OpenAI, Anthropic) e, sub capotă, un wrapper mai sofisticat peste exact acest pattern — construiește cererea HTTP, adaugă header-ele de autentificare, gestionează retry-uri și timeout-uri, parsează răspunsul JSON. Dacă vreodată un SDK are un bug sau nu suportă o funcționalitate nouă, poți întotdeauna "coborî" la `requests` direct, construind manual cererea către endpoint-ul documentat al API-ului — cunoștințele din această lecție rămân aplicabile universal, indiferent de SDK-ul din jur.
</CosmoHint>

### Upload de fișiere — `files=`

```python
with open("imagine.jpg", "rb") as f:
    raspuns = requests.post(
        "https://api.exemplu.ro/upload",
        files={"fisier": f}    # construiește automat un request multipart/form-data (revezi C3 L20)
    )
```

Parametrul `files=` construiește automat o cerere `multipart/form-data`, formatul standard HTTP pentru transmiterea de fișiere binare alături de câmpuri text obișnuite — util pentru API-uri care acceptă upload-uri de imagini, documente, sau alte fișiere. Combinat cu modul binar de deschidere a fișierelor (`"rb"`, revizitat complet în L22), acest pattern acoperă majoritatea cazurilor practice de upload direct din Python.

### Descărcarea de fișiere mari — streaming, nu totul deodată

```python
raspuns = requests.get("https://exemplu.ro/fisier_mare.zip", stream=True, timeout=30)
with open("descarcare.zip", "wb") as f:
    for bucata in raspuns.iter_content(chunk_size=8192):
        f.write(bucata)
```

`stream=True` schimbă comportamentul implicit al `requests`: în loc să descarce tot conținutul răspunsului în memorie înainte să-l returneze, permite citirea lui **progresivă**, bucată cu bucată, prin `.iter_content()` — exact principiul deja familiar de la generatoare (L19) și citirea de fișiere mari (L22), aplicat aici transferurilor de rețea. Pentru fișiere de dimensiuni mari (modele AI descărcate, seturi de date), acest pattern previne alocarea unei cantități masive de memorie doar pentru a ține tot răspunsul, neîntrerupt, înainte de a-l scrie pe disc.

### Verificarea header-elor de răspuns

```python
raspuns = requests.get("https://api.exemplu.ro/date")
print(raspuns.headers["Content-Type"])        # 'application/json'
print(raspuns.headers.get("X-RateLimit-Remaining"))   # câte cereri mai ai la dispoziție (revezi C3 L22)
print(raspuns.elapsed.total_seconds())            # cât a durat efectiv cererea
```

Header-ele de răspuns (`.headers`, un dicționar-like) conțin des informații operaționale utile dincolo de conținutul propriu-zis — limitele de rate limiting rămase (`X-RateLimit-Remaining`, revezi C3 L22), tipul de conținut, sau metadate custom specifice API-ului apelat. `.elapsed` măsoară automat durata cererii, util pentru logging și diagnosticare de performanță fără cronometrare manuală explicită.

### `httpx` — succesorul modern, compatibil sincron și async

```python
import httpx

# Sincron, sintaxă aproape identică cu requests:
raspuns = httpx.get("https://api.exemplu.ro/date")

# Asincron, direct legat de L21:
async def obtine_date_async():
    async with httpx.AsyncClient() as client:
        raspuns = await client.get("https://api.exemplu.ro/date")
        return raspuns.json()
```

`httpx`, menționat deja în L21 pentru capacitatea lui async, oferă și o interfață sincronă aproape identică sintactic cu `requests` — motiv pentru care multe proiecte noi aleg `httpx` de la început, chiar dacă folosesc inițial doar codul sincron, pentru a avea opțiunea de a trece la async mai târziu fără să schimbe complet biblioteca folosită.

### Redirectări automate — `allow_redirects`

```python
raspuns = requests.get("http://exemplu.ro", allow_redirects=True)   # implicit True
print(raspuns.history)   # lista tuturor redirectărilor (301, 302) urmate automat
print(raspuns.url)         # URL-ul FINAL, după toate redirectările
```

`requests` urmează automat redirectările HTTP (`301 Moved Permanently`, `302 Found`, revezi C3 L20), transparent, fără cod suplimentar — comportament implicit, dezactivabil explicit cu `allow_redirects=False` pentru cazuri unde vrei să inspectezi manual redirectarea, nu s-o urmezi automat (util la debugging sau la verificarea explicită a unei politici de securitate care nu ar trebui să urmeze redirectări către domenii neîncrezătoare).

### `PreparedRequest` — inspectarea cererii înainte de trimitere

```python
cerere = requests.Request("POST", "https://api.exemplu.ro/date", json={"cheie": "valoare"})
pregatita = cerere.prepare()
print(pregatita.headers)   # header-ele EXACTE care vor fi trimise
print(pregatita.body)        # body-ul EXACT, deja serializat

with requests.Session() as sesiune:
    raspuns = sesiune.send(pregatita)
```

Pentru cazuri avansate — debugging al unei cereri care nu se comportă cum te-ai aștepta, sau construirea manuală de semnături criptografice peste conținutul exact al cererii (exact pattern-ul discutat la webhook-uri, C3 L24) — `Request`/`prepare()` expune conținutul complet, byte cu byte, al ce va fi trimis efectiv pe rețea, înainte ca cererea să plece — util pentru a verifica exact ce trimite biblioteca, fără presupuneri.

### Proxy-uri — rutarea cererilor prin intermediari

```python
proxy_uri = {
    "http": "http://proxy.exemplu.ro:8080",
    "https": "http://proxy.exemplu.ro:8080",
}
raspuns = requests.get("https://api.exemplu.ro/date", proxies=proxy_uri, timeout=10)
```

Parametrul `proxies=` rutează cererea printr-un server proxy (revezi conceptul de forward proxy din C3) — util pentru medii corporate care impun trafic prin proxy central, sau pentru testare din locații geografice diferite prin proxy-uri dedicate. Configurarea diferă pentru `http`/`https`, permițând proxy-uri separate pentru fiecare protocol, dacă infrastructura o cere.

### Testarea codului care face cereri HTTP — mock-uri

Cod care depinde de apeluri de rețea reale e greu de testat automat — testele ar deveni lente, fragile (dependente de disponibilitatea serviciului extern), și costisitoare (cereri reale repetate la fiecare rulare de test). Biblioteca `unittest.mock` (sau `responses`, o bibliotecă dedicată specific pentru `requests`) permite "simularea" răspunsurilor HTTP, fără nicio cerere reală de rețea:

```python
from unittest.mock import patch, Mock

@patch("requests.get")
def test_obtine_utilizator(mock_get):
    mock_get.return_value = Mock(status_code=200, json=lambda: {"nume": "Ana"})

    rezultat = obtine_utilizator(42)   # funcția TESTATĂ apelează requests.get intern
    assert rezultat["nume"] == "Ana"
```

`@patch("requests.get")` înlocuiește temporar funcția reală `requests.get` cu un obiect fals (`Mock`), controlat complet de test — funcția testată nu observă nicio diferență (tot apelează "requests.get" ca de obicei), dar niciun byte nu circulă efectiv prin rețea. Acest pattern e esențial pentru orice suită de teste automate care acoperă cod de integrare cu API-uri externe, inclusiv apeluri către modele AI, unde testele reale, cu costuri și latență reală, ar fi impracticabile de rulat la fiecare modificare de cod.

Testele care mock-uiesc apeluri API verifică logica proprie de gestionare a răspunsului (parsare, validare, tratarea erorilor) — nu verifică dacă API-ul real răspunde corect, o distincție importantă: teste unitare mock-uite completează, dar nu înlocuiesc complet, teste de integrare ocazionale, rulate separat, care chiar apelează serviciul real pentru a confirma că integrarea funcționează end-to-end.

## REVEAL

{/* TABLE */}

| Nevoie | Cod |
|---|---|
| Cerere GET simplă | `requests.get(url)` |
| Trimite JSON în body | `requests.post(url, json=date)` |
| Autentificare prin header | `requests.get(url, headers={"Authorization": "Bearer ..."})` |
| Eroare la timeout, nu blocare infinită | `requests.get(url, timeout=5)` |
| Verificare explicită de succes | `raspuns.raise_for_status()` |
| Reutilizare conexiune pentru mai multe cereri | `requests.Session()` |

<FactBox>
**Requests în cifre:**
- Creat de Kenneth Reitz, lansat în **2011**
- `raspuns.json()` poate arunca `JSONDecodeError` indiferent de status code — sunt garanții separate
- `timeout=`: fără el, o cerere poate aștepta indefinit — echivalentul unei bucle infinite la nivel de rețea
- `raise_for_status()`: NU se apelează automat — `4xx`/`5xx` nu aruncă excepție implicit
- `requests.Session()`: reutilizează conexiunea TCP/TLS, evită handshake complet la fiecare cerere
- Backoff exponențial standard: 1s, 2s, 4s, 8s... — pattern universal pentru retry la eșecuri temporare
</FactBox>

## ÎNCHEIERE

`requests` transformă teoria protocolului HTTP din C3 în cod executabil, concret: metode, header-e, autentificare, gestionare de erori — toate reduse la câteva linii clare, lizibile. Regulile de producție rămân constante: mereu `timeout=`, mereu `raise_for_status()` sau verificare explicită de status, mereu gestionare de excepții specifice pentru eșecuri de rețea.

Ai văzut `json=` folosit deja de câteva ori, fără explicație completă. Lecția următoare dedică timpul necesar modulului `json` și bibliotecii Pydantic — validarea structurată a datelor, esențială pentru orice integrare serioasă cu modele AI care necesită structured outputs.
