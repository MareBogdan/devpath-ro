# Dicționare (Hash Maps): Acces O(1)

## HOOK

Un răspuns JSON de la o API AI (C3 L20) conține câmpuri numite — `"model"`, `"usage"`, `"choices"` — nu poziții numerice. `raspuns[2]` n-ar avea niciun sens; `raspuns["choices"]` comunică exact ce vrei. Mai mult, cauți acest câmp printre potențial mii de câmpuri posibile, și vrei ca timpul de căutare să rămână **la fel de rapid** indiferent dacă structura are 3 câmpuri sau 3 milioane.

Un **dicționar** rezolvă exact ambele nevoi: acces prin **cheie** (nu poziție numerică) și timp de căutare aproape constant — `O(1)` — indiferent de dimensiunea colecției. Această garanție de performanță nu e o coincidență de implementare, e rezultatul direct al unei structuri de date fundamentale din informatică: hash map-ul.

---

## CONTEXT

**Hash map**-ul (sau hash table) e una din cele mai importante structuri de date din toată informatica — inventat conceptual în anii '50, rafinat constant de atunci. Ideea de bază: în loc să cauți o valoare comparând-o secvențial cu fiecare element existent (`O(n)`, cum ar face o listă), calculezi o **funcție de hash** peste cheie, care produce direct un index în memorie unde ar trebui să fie stocată valoarea — cauți la acea poziție exactă, fără să compari cu nimic altceva.

Dicționarele Python au avut o evoluție notabilă de implementare: până la Python 3.6, ordinea elementelor unui dicționar **nu era garantată** — putea diferi între execuții. Din **Python 3.7**, ordinea de inserare e garantată oficial, ca parte a specificației limbajului (nu doar un detaliu de implementare) — o schimbare care a simplificat mult cod care se baza implicit pe ordinea în care fuseseră adăugate cheile.

## MIEZUL

### Creare, acces, modificare

```python
utilizator = {
    "nume": "Ana",
    "varsta": 25,
    "activ": True
}

print(utilizator["nume"])        # "Ana" — acces direct prin cheie
utilizator["oras"] = "Cluj"        # adaugă o cheie NOUĂ
utilizator["varsta"] = 26          # MODIFICĂ o cheie existentă
del utilizator["activ"]             # elimină o cheie

print(utilizator["inexistent"])    # KeyError! — cheia nu există
print(utilizator.get("inexistent", "N/A"))   # "N/A" — .get() cu valoare implicită, FĂRĂ eroare
```

`[]` aruncă `KeyError` direct dacă cheia nu există — util când **te aștepți** ca cheia să existe și vrei să afli imediat, clar, dacă nu e cazul (revezi filosofia `try`/`except` din L11). `.get(cheie, implicit)` e varianta sigură, care nu aruncă nicio eroare — preferată când absența cheii e un caz normal, așteptat, nu o eroare de gestionat.

<CosmoHint emotion="thinking">
De ce cheile unui dicționar trebuie să fie IMUTABILE (string, int, tuple — nu listă)? Pentru că hash map-ul calculează hash-ul cheii O SINGURĂ DATĂ, la inserare, și folosește acea valoare pentru a determina poziția de stocare. Dacă cheia s-ar putea modifica după inserare (ca o listă mutabilă), hash-ul ei s-ar schimba, dar poziția în memorie unde a fost deja stocată nu — dicționarul n-ar mai putea găsi valoarea căutând după noul hash. Python previne complet problema: `{[1,2]: "valoare"}` aruncă direct `TypeError: unhashable type: 'list'` la definire.
</CosmoHint>

### Metode esențiale — iterare completă

```python
utilizator = {"nume": "Ana", "varsta": 25, "oras": "Cluj"}

for cheie in utilizator:                    # iterează implicit peste CHEI
    print(cheie)

for cheie, valoare in utilizator.items():    # cheie ȘI valoare simultan
    print(f"{cheie}: {valoare}")

for valoare in utilizator.values():          # doar valorile
    print(valoare)

print(list(utilizator.keys()))               # ['nume', 'varsta', 'oras']
print("nume" in utilizator)                   # True — verifică EXISTENȚA unei chei
```

`in` pe un dicționar verifică existența unei **chei**, nu a unei valori — și, la fel ca accesul prin `[]`, e tot `O(1)`, nu necesită parcurgerea tuturor cheilor — un avantaj masiv față de `in` pe o listă, unde verificarea e `O(n)`, liniară în numărul de elemente.

{/* TABLE */}

| Operațiune | Listă | Dicționar |
|---|---|---|
| Acces prin poziție/cheie | `lista[0]` — O(1) | `dict["cheie"]` — O(1) |
| Verificare existență (`in`) | O(n) — parcurge secvențial | **O(1)** — hash direct |
| Căutare valoare specifică | O(n) | O(n) — doar CHEILE au acces rapid |
| Ordinea elementelor | Garantată, ordinea de inserare | Garantată din Python 3.7, ordinea de inserare |
| Chei/indici permise | Numai poziții numerice | Orice tip imutabil (str, int, tuple) |

### `defaultdict` și `.setdefault()` — evitarea `KeyError` la agregare

Un pattern extrem de comun: construirea unui dicționar prin agregare, unde fiecare cheie nouă are nevoie de o valoare implicită (o listă goală, un contor la 0) înainte de a putea fi extinsă:

```python
from collections import defaultdict

grupuri = defaultdict(list)   # orice cheie NOUĂ primește automat o listă vidă implicit
grupuri["fructe"].append("măr")
grupuri["fructe"].append("pară")
grupuri["legume"].append("morcov")

print(dict(grupuri))   # {'fructe': ['măr', 'pară'], 'legume': ['morcov']}
```

Fără `defaultdict`, ai avea nevoie de o verificare explicită la fiecare adăugare (`if cheie not in grupuri: grupuri[cheie] = []`) — `defaultdict` elimină acest boilerplate, creând automat valoarea implicită prima dată când o cheie e accesată, dacă nu exista deja.

### Dict comprehensions — construcție concisă

```python
numere = [1, 2, 3, 4]
patrate = {n: n ** 2 for n in numere}   # {1: 1, 2: 4, 3: 9, 4: 16}

# Inversarea unui dicționar (cheie <-> valoare):
original = {"a": 1, "b": 2}
inversat = {v: k for k, v in original.items()}   # {1: 'a', 2: 'b'}
```

Aceeași idee de list comprehension din L7/L18, aplicată dicționarelor — construiești un dicționar nou printr-o expresie compactă, în loc de o buclă explicită cu `.items()`.

<CosmoHint emotion="encouraging">
Configurările de model AI sunt aproape universal reprezentate ca dicționare — `parametri = {"temperature": 0.7, "max_tokens": 500, "top_p": 0.9}`, transmis apoi direct ca `**parametri` la o funcție (revezi `**kwargs` din L9). Un JSON de configurare, citit dintr-un fișier, se încarcă direct ca dicționar Python prin `json.loads()` (detalii complete în L24) — legătura dintre JSON și dicționar e practic 1-la-1, motiv pentru care ambele structuri se simt aproape identice de folosit.
</CosmoHint>

### Când NU folosești un dicționar

Dacă ordinea numerică e semnificația de bază a datelor tale (o secvență de pași, un istoric cronologic simplu), o listă e alegerea corectă — dicționarul adaugă complexitate inutilă pentru un caz unde poziția *este* semnificația. Dicționarul câștigă exact când accesul e natural prin *nume/identificator*, nu prin *poziție* — utilizatori identificați prin ID, configurări identificate prin nume de parametru, contoare identificate prin categorie.

### `Counter` — numărarea frecvenței, un caz specializat de dicționar

Un pattern extrem de comun — numărarea de câte ori apare fiecare element distinct dintr-o colecție — are o unealtă dedicată în biblioteca standard, mai directă decât un `defaultdict(int)` scris manual:

```python
from collections import Counter

cuvinte = ["python", "ai", "python", "model", "ai", "python"]
frecvente = Counter(cuvinte)

print(frecvente)                  # Counter({'python': 3, 'ai': 2, 'model': 1})
print(frecvente["python"])          # 3
print(frecvente.most_common(2))       # [('python', 3), ('ai', 2)] — cele mai frecvente 2
```

`Counter` e, tehnic, o subclasă de `dict`, cu comportament suplimentar util: accesul la o cheie inexistentă returnează `0` implicit (nu `KeyError`), și metoda `.most_common(n)` returnează direct top N elemente după frecvență, sortate descrescător — exact operațiunea pe care ai construi-o manual, cu mai multe linii, folosind `sorted()` cu `key=` (revezi L12) peste `.items()` ale unui dicționar obișnuit.

### `Counter` pentru numărarea vocabularului — legătura cu AI

Construirea unui vocabular de tokeni dintr-un corpus de text — pas fundamental în orice pipeline de procesare de limbaj natural — se reduce, la nivelul cel mai simplu, la exact acest pattern:

```python
text = "modelul procesează text modelul învață din text"
tokeni = text.split()
frecventa_tokenilor = Counter(tokeni)

vocabular = [token for token, count in frecventa_tokenilor.most_common(1000)]   # top 1000 cele mai frecvente
```

Vocabularele reale ale modelelor de limbaj (tokenizatoare BPE, folosite de GPT și modele similare) sunt construite prin algoritmi mult mai sofisticați decât o simplă numărare de cuvinte — dar principiul de bază, "numără frecvența fiecărei unități distincte, păstrează-le pe cele mai relevante," rămâne conceptual identic celui demonstrat aici, la scară mult mai mare și cu unități mai fine decât cuvinte întregi (sub-cuvinte, caractere individuale).

### `OrderedDict` — o relicvă istorică, azi aproape inutilă

Înainte de Python 3.7 (când ordinea de inserare a devenit garantată pentru dicționarele obișnuite, menționat deja în CONTEXT), `collections.OrderedDict` era singura structură care garanta explicit păstrarea ordinii. Azi rămâne utilă doar pentru câteva capacități suplimentare specifice (comparație de egalitate sensibilă la ordine, metoda `.move_to_end()`) — pentru marea majoritate a cazurilor de uz, un `dict` obișnuit e complet suficient, iar `OrderedDict` apare azi mai ales în cod mai vechi, scris înainte de garanția oficială de ordine.

### Fuzionarea dicționarelor — combinarea mai multor surse de configurare

Un scenariu practic frecvent: combinarea unor valori implicite cu configurări specifice furnizate de utilizator, unde cele din urmă trebuie să aibă prioritate:

```python
implicite = {"temperature": 0.7, "max_tokens": 500, "model": "gpt-4o-mini"}
custom = {"temperature": 0.2}

# Operatorul '|' (Python 3.9+) — combină două dicționare, al doilea are prioritate la chei comune:
final = implicite | custom
print(final)   # {'temperature': 0.2, 'max_tokens': 500, 'model': 'gpt-4o-mini'}

# Echivalent mai vechi, compatibil cu versiuni Python anterioare:
final_alt = {**implicite, **custom}   # despachetare cu '**', ultima sursă câștigă la coliziuni
```

Ambele forme produc un dicționar **nou**, fără să modifice niciunul dintre cele originale — util constant pentru pattern-ul "valori implicite, suprascrise selectiv de configurare specifică," întâlnit la fiecare apel către o API configurabilă (parametri impliciți de model, suprascriși explicit doar acolo unde utilizatorul specifică o valoare diferită).

### `.update()` — fuzionare cu modificare în loc

```python
configurare = {"temperature": 0.7, "max_tokens": 500}
configurare.update({"temperature": 0.2, "top_p": 0.9})
print(configurare)   # {'temperature': 0.2, 'max_tokens': 500, 'top_p': 0.9} — MODIFICAT în loc
```

Spre deosebire de `|` (creează un dicționar nou), `.update()` modifică dicționarul existent direct, adăugând chei noi și suprascriind cele existente cu valorile din argumentul primit — aceeași distincție filozofică repetată constant în acest curs: o operațiune care creează un obiect nou vs. una care modifică în loc, cu implicații directe asupra oricărei alte variabile care mai referențiază același obiect (revezi L16).

### Chei imbricate și `.get()` în lanț — evitarea `KeyError` pe structuri adânci

```python
raspuns = {"data": {"utilizator": {"nume": "Ana"}}}

# Risc de KeyError la orice nivel dacă structura nu e exact cea așteptată:
nume = raspuns["data"]["utilizator"]["nume"]

# Variantă sigură, cu .get() înlănțuit, fiecare cu valoare implicită de dicționar gol:
nume_sigur = raspuns.get("data", {}).get("utilizator", {}).get("nume", "necunoscut")
```

Acest pattern — `.get()` înlănțuit, fiecare cu un dicționar gol ca valoare implicită — evită excepțiile la orice nivel lipsă din structura imbricată, comun la parsarea de răspunsuri JSON de la API-uri externe unde structura exactă nu e mereu garantată complet. Pentru validare mai riguroasă și mai lizibilă a structurilor complexe, Pydantic (L24) automatizează complet acest tip de verificare, eliminând nevoia de lanțuri lungi de `.get()`.

### `.pop()` cu valoare implicită — eliminare sigură

```python
setari = {"debug": True, "verbose": False}

valoare = setari.pop("debug")              # elimină ȘI returnează valoarea — True
valoare_lipsa = setari.pop("inexistent", "N/A")   # nu aruncă eroare, returnează "N/A"
```

`.pop()` pe un dicționar combină două operațiuni într-una: elimină cheia și returnează valoarea ei, similar conceptual cu `.pop()` de pe o listă (L12), dar identificând elementul prin cheie, nu prin index. Al doilea argument, opțional, oferă o valoare implicită dacă cheia nu există — exact aceeași convenție de siguranță ca `.get()`, aplicată eliminării în loc de simplei citiri.

### Dicționare ca cache simplu — memoizare manuală

Un pattern practic direct legat de `lru_cache` (menționat deja la decoratori, L20): un dicționar poate servi ca un cache manual, simplu, pentru rezultate costisitoare de calculat:

```python
cache_rezultate = {}

def calculeaza_scump(n):
    if n in cache_rezultate:
        return cache_rezultate[n]           # rezultat deja calculat, returnat instant
    rezultat = n ** n                          # operațiune presupusă costisitoare
    cache_rezultate[n] = rezultat                # salvează pentru apeluri viitoare
    return rezultat
```

Acest pattern — verifică dacă rezultatul există deja în dicționar, calculează și salvează doar dacă lipsește — se numește **memoizare**, o tehnică de optimizare extrem de comună, aplicabilă oricărei funcții pure (revezi L9) ale cărei rezultate depind exclusiv de argumentele primite, fără efecte secundare care ar face cache-ul invalid. `functools.lru_cache` automatizează exact acest pattern, fără să scrii manual dicționarul de cache — dar înțelegerea versiunii manuale, explicite, ajută la a recunoaște imediat ce face decoratorul atunci când îl întâlnești în cod real.

## REVEAL

{/* TABLE */}

| Nevoie | Metodă |
|---|---|
| Acces sigur, cu valoare implicită dacă cheia nu există | `.get(cheie, implicit)` |
| Verificare existență cheie | `cheie in dictionar` |
| Iterare cheie + valoare simultan | `.items()` |
| Agregare cu valoare implicită automată | `defaultdict(list)` sau `defaultdict(int)` |
| Construcție concisă dintr-o transformare | dict comprehension |

<FactBox>
**Dicționare în cifre:**
- Acces prin cheie: complexitate medie **O(1)** — constant, indiferent de numărul de chei
- Ordinea de inserare: garantată oficial din **Python 3.7** (2018), doar de implementare înainte
- Chei valide: doar tipuri **imutabile** — string, int, float, tuple (nu listă, nu dicționar)
- `defaultdict`: parte din modulul standard `collections`
- JSON ↔ dicționar Python: mapare aproape 1-la-1 prin `json.loads()`/`json.dumps()` (detalii L24)
- `in` pe dicționar (chei) vs. listă: O(1) vs. O(n) — diferență critică la colecții mari
</FactBox>

## ÎNCHEIERE

Dicționarele oferă exact ce listele nu pot: acces prin identificator semantic, nu poziție numerică, cu performanță constantă indiferent de dimensiune. Combinația listă + dicționar acoperă majoritatea nevoilor de structurare a datelor în cod Python real — și amândouă sunt **mutabile**, cu toate consecințele deja discutate în L3 și L12 despre referințe partajate.

Nu toate colecțiile trebuie să fie modificabile, însă. Lecția următoare introduce tuple-urile — practic liste, dar cu o garanție structurală importantă: odată create, nu se pot schimba niciodată.
