# Clase: Cât să citești un model PyTorch

## HOOK

```python
class ReteaNeuronala(nn.Module):
    def __init__(self, dimensiune_input, dimensiune_output):
        super().__init__()
        self.strat1 = nn.Linear(dimensiune_input, 128)
        self.strat2 = nn.Linear(128, dimensiune_output)

    def forward(self, x):
        x = torch.relu(self.strat1(x))
        return self.strat2(x)
```

Deschide fișierul de definire a aproape oricărui model PyTorch și vei găsi exact acest tipar — o `class`, un `__init__`, un `super().__init__()`, o metodă `forward`. Nu ai nevoie să devii expert în programare orientată pe obiecte pentru a citi cod AI, dar fără să înțelegi ce reprezintă efectiv aceste patru elemente, codul de model rămâne o secvență opacă de simboluri magice, memorate mecanic, nu înțelese.

Scopul acestei lecții e minim și precis, exact ca titlul: nu te face expert OOP — te face capabil să citești și să modifici o clasă de model AI cu încredere reală.

---

## CONTEXT

Programarea orientată pe obiecte (OOP) — organizarea codului în jurul unor **obiecte** care combină date (atribute) și comportament (metode) — a apărut din Smalltalk (anii '70) și a devenit dominantă prin C++ și Java în anii '90. Ideea centrală: în loc să ai funcții separate care operează pe structuri de date pasive, grupezi datele **și** funcțiile care le manipulează într-o singură unitate coerentă, numită clasă.

Python suportă OOP complet, dar fără a-l impune — poți scrie programe Python întregi, funcționale, fără nicio clasă proprie (ai făcut-o în toate lecțiile de până acum). Clasele devin necesare când modelezi entități cu **stare internă persistentă** și comportament asociat — exact cazul unui model de rețea neuronală, care are stare (ponderile straturilor) și comportament (cum transformă un input în output).

## MIEZUL

### Anatomia minimă a unei clase

```python
class Utilizator:
    def __init__(self, nume, varsta):    # constructor — rulează la CREAREA unui obiect nou
        self.nume = nume                    # atribut de INSTANȚĂ
        self.varsta = varsta

    def prezentare(self):                  # METODĂ — funcție care aparține clasei
        return f"{self.nume}, {self.varsta} ani"

ana = Utilizator("Ana", 25)      # creează o INSTANȚĂ (obiect concret) a clasei
print(ana.prezentare())            # "Ana, 25 ani"
print(ana.nume)                      # acces direct la atribut: "Ana"
```

`class Utilizator:` definește un **șablon** (blueprint) — clasa în sine nu e un utilizator concret, e "forma" pe care o vor avea toți utilizatorii creați din ea. `__init__` (constructorul) rulează automat de fiecare dată când creezi o instanță nouă (`Utilizator("Ana", 25)`) — inițializează starea internă a acelui obiect specific.

<CosmoHint emotion="thinking">
De ce fiecare metodă are `self` ca prim parametru, dar nu-l pasezi explicit la apel (`ana.prezentare()`, nu `ana.prezentare(ana)`)? `self` reprezintă instanța specifică pe care o apelezi metoda — Python îl transmite AUTOMAT, implicit, la fiecare apel `obiect.metoda(...)`. `self.nume` din interiorul metodei se referă la atributul `nume` al ACELUI obiect specific, nu al unui alt utilizator creat din aceeași clasă. Fără `self`, o metodă n-ar avea nicio modalitate de a accesa starea proprie a instanței pe care a fost apelată.
</CosmoHint>

### `nn.Module` — moștenirea, explicată pe cazul care contează

```python
class ReteaNeuronala(nn.Module):   # 'ReteaNeuronala' MOȘTENEȘTE din nn.Module
    def __init__(self, dimensiune_input, dimensiune_output):
        super().__init__()          # apelează constructorul CLASEI PĂRINTE (nn.Module) ÎNTÂI
        self.strat1 = nn.Linear(dimensiune_input, 128)
        self.strat2 = nn.Linear(128, dimensiune_output)
```

`class ReteaNeuronala(nn.Module):` — sintaxa `(nn.Module)` declară **moștenire**: `ReteaNeuronala` obține automat tot comportamentul definit deja în clasa `nn.Module` din PyTorch — urmărirea automată a parametrilor antrenabili, mutarea pe GPU (`.to("cuda")`), salvarea/încărcarea ponderilor, și multe altele — fără să scrii tu vreo linie din acea logică. Clasa ta adaugă doar ce e specific arhitecturii tale: ce straturi conține, cum le combină.

`super().__init__()` — apelează explicit constructorul clasei părinte (`nn.Module`), **înainte** de a-ți defini propriile straturi. Fără acest apel, mecanismele interne din `nn.Module` (care urmăresc automat toate straturile pe care le atribui prin `self.strat1 = ...`) nu s-ar inițializa corect — o omisiune extrem de comună la cod scris de începători, care produce erori confuze mai târziu, la antrenare.

{/* TABLE */}

| Concept | Rol în exemplul PyTorch |
|---|---|
| `class X(Parinte):` | Declară moștenirea — `X` obține comportamentul lui `Parinte` |
| `super().__init__()` | Inițializează corect partea din clasa părinte, înainte de restul |
| `self.strat1 = nn.Linear(...)` | Atribut de instanță — un strat specific ACESTUI model |
| `def forward(self, x):` | Metodă — logica de propagare înainte, specifică arhitecturii |

### `forward()` — de ce nu se apelează direct, dar rulează la `model(x)`

```python
model = ReteaNeuronala(10, 2)
rezultat = model(date_input)    # apelezi modelul CA O FUNCȚIE, nu model.forward(date_input) direct
```

Convenția PyTorch — apelarea unui model ca o funcție (`model(x)`), nu ca o metodă explicită (`model.forward(x)`) — funcționează pentru că `nn.Module` (clasa părinte) definește metoda specială `__call__`, care face verificări suplimentare (hooks, mod de antrenare vs. evaluare) și **apelează** `forward()` intern, automat. Convenția din bibliotecă e să apelezi mereu modelul direct, niciodată `.forward()` manual — chiar dacă tehnic ai avea acces direct la ea.

### Atribute vs. metode — starea vs. comportamentul

```python
class ContBancar:
    def __init__(self, sold_initial):
        self.sold = sold_initial          # ATRIBUT — datele, starea internă

    def depune(self, suma):                 # METODĂ — comportamentul care modifică starea
        self.sold += suma

    def retrage(self, suma):
        if suma > self.sold:
            raise ValueError("Fonduri insuficiente")
        self.sold -= suma
```

Fiecare instanță (`ContBancar(100)`, `ContBancar(500)`) are propriile atribute independente — modificarea soldului unui cont nu afectează celălalt, exact cum modificarea ponderilor unui model de rețea neuronală nu afectează o instanță separată a aceleiași arhitecturi (antrenată pe alte date, cu alte valori inițiale).

### Convenția underscore — semnalul de "intern", nu impunere

```python
class Model:
    def __init__(self):
        self.public = "acces liber"
        self._intern = "convenție: nu accesa direct din afară"
        self.__foarte_privat = "name mangling — accesare mai greoaie intenționat"
```

Revizitând convenția menționată în L3: `_intern` (un underscore) semnalează "intenționat pentru uz intern", fără nicio restricție tehnică reală — Python nu are `private`/`public` ca Java. `__foarte_privat` (dublu underscore) declanșează **name mangling** — Python redenumește intern atributul (`_Model__foarte_privat`), făcând accesul accidental din afara clasei mai greoi, dar tot nu impossibil. Codul PyTorch/scikit-learn folosește frecvent underscore simplu pentru atribute interne (`model._modules`), un semnal clar "nu te baza pe asta direct, poate schimba fără avertisment".

<CosmoHint emotion="encouraging">
`model.parameters()` — o metodă expusă de `nn.Module` — returnează un generator (concept detaliat în L19) peste toți parametrii antrenabili din model, colectați automat din toate atributele `self.strat...` definite în `__init__`. Nu trebuie să adaugi manual niciun strat la o listă separată de parametri — moștenirea din `nn.Module` face asta transparent, exact motivul pentru care fiecare model PyTorch trebuie să extindă `nn.Module`, nu doar să fie o clasă obișnuită de sine stătătoare.
</CosmoHint>

### Metode speciale (dunder) — `__init__` nu e singura

`__init__` e cea mai cunoscută metodă specială (dunder — "double underscore"), dar Python definește zeci de altele, fiecare apelată implicit de o operație sau sintaxă specifică:

```python
class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):           # apelată de print(), repr(), sau afișarea în REPL
        return f"Vector({self.x}, {self.y})"

    def __eq__(self, altul):       # apelată de '==' (revezi L5, suprascrierea operatorilor)
        return self.x == altul.x and self.y == altul.y

    def __len__(self):              # apelată de len(obiect)
        return int((self.x**2 + self.y**2) ** 0.5)

v1 = Vector(3, 4)
print(v1)              # Vector(3, 4) — folosește __repr__
print(len(v1))           # 5 — folosește __len__
print(v1 == Vector(3, 4))  # True — folosește __eq__
```

Fără `__repr__` definit explicit, `print(v1)` ar afișa ceva de forma `<__main__.Vector object at 0x7f...>` — adresa de memorie brută, complet neinformativă. Fără `__eq__`, `==` ar compara implicit prin identitate (`is`), nu prin conținut — două instanțe cu aceleași valori `x`/`y` ar fi considerate "diferite". Aceste metode speciale sunt mecanismul prin care clasele custom se integrează natural cu sintaxa și funcțiile încorporate ale limbajului, exact ca operatorii suprascriși din L5.

### Metode de clasă și metode statice — `@classmethod`, `@staticmethod`

```python
class Utilizator:
    numar_total = 0   # atribut de CLASĂ — partajat de TOATE instanțele, nu per-instanță

    def __init__(self, nume):
        self.nume = nume
        Utilizator.numar_total += 1

    @classmethod
    def din_dictionar(cls, date):        # 'cls' = clasa însăși, nu o instanță
        return cls(date["nume"])

    @staticmethod
    def este_nume_valid(nume):            # NU primește nici self, nici cls — funcție "atașată" clasei
        return len(nume) > 0

u1 = Utilizator.din_dictionar({"nume": "Ana"})   # constructor alternativ
print(Utilizator.este_nume_valid("Ion"))            # True — apelabilă direct pe clasă
```

`@classmethod` primește clasa însăși (`cls`), nu o instanță — util pentru constructori alternativi, ca `din_dictionar` de mai sus, care construiesc o instanță dintr-o formă diferită de date de intrare. `@staticmethod` nu primește nici `self`, nici `cls` — e, efectiv, o funcție obișnuită, grupată logic în interiorul clasei doar pentru organizare, fără să aibă nevoie de acces la starea vreunei instanțe sau a clasei. Atributele de clasă (`numar_total`, definit direct în corpul clasei, nu în `__init__`) sunt partajate între **toate** instanțele — o distincție importantă față de atributele de instanță (`self.nume`), fiecare independent per obiect creat.

### Moștenire multiplă și `super()` în lanțuri mai lungi

L17 a introdus deja moștenirea simplă, cu un singur `super().__init__()`. Python suportă și **moștenire multiplă** — o clasă poate extinde simultan mai multe clase părinte:

```python
class Salvabil:
    def salveaza(self):
        print("Salvat pe disc")

class Loghabil:
    def logheaza(self, mesaj):
        print(f"LOG: {mesaj}")

class Model(Salvabil, Loghabil):   # extinde AMBELE clase simultan
    pass

m = Model()
m.salveaza()             # "Salvat pe disc" — moștenit de la Salvabil
m.logheaza("test")         # "LOG: test" — moștenit de la Loghabil
```

Ordinea claselor părinte în paranteze determină **MRO** (Method Resolution Order) — ordinea în care Python caută o metodă, dacă mai multe clase părinte ar defini-o cu același nume. Moștenirea multiplă e puternică, dar poate deveni rapid confuză cu hierarhii adânci — motiv pentru care multe echipe preferă **compoziția** (o clasă care conține o instanță a alteia, ca atribut, în loc să extindă direct) atunci când relația nu e strict de tip "este un", ci mai degrabă "are un".

Regula practică de decizie, cunoscută larg ca principiul "composition over inheritance": moștenește doar când noua clasă *este cu adevărat* o variantă specializată a părintelui (un `Caine` este cu adevărat un `Animal`); când relația e mai degrabă "folosește" sau "conține" (un `Model` care folosește un `Logger` pentru a-și înregistra evenimentele, dar nu este el însuși un logger), compoziția — un atribut care conține o instanță separată — produce, de regulă, un design mai flexibil și mai ușor de întreținut pe termen lung.

### `isinstance()` cu clase custom — moștenirea recunoscută automat

```python
class Animal:
    pass

class Caine(Animal):
    pass

c = Caine()
print(isinstance(c, Caine))    # True
print(isinstance(c, Animal))     # True — 'Caine' MOȘTENEȘTE din 'Animal'
print(isinstance(c, object))       # True — TOATE clasele moștenesc, ultimativ, din 'object'
```

Exact ca `isinstance(True, int)` din L4 (unde `bool` e subclasă de `int`), `isinstance()` respectă lanțul complet de moștenire pentru orice clasă custom — un `Caine` e simultan o instanță de `Caine`, de `Animal` (părintele), și de `object` (rădăcina universală a oricărei clase Python, moștenită implicit de orice altă clasă, chiar și fără să o declari explicit).

### Docstrings de clasă — documentarea completă a unui model

```python
class ReteaNeuronala(nn.Module):
    """Rețea feedforward simplă cu două straturi liniare.

    Args:
        dimensiune_input: numărul de caracteristici de intrare.
        dimensiune_output: numărul de clase de ieșire.
    """
    def __init__(self, dimensiune_input, dimensiune_output):
        super().__init__()
        ...
```

Exact ca la funcții (L9), un docstring plasat imediat sub `class NumeClasa:` documentează întreaga clasă, accesibil prin `help(ReteaNeuronala)` sau `ReteaNeuronala.__doc__`. Cod de model AI serios, destinat să fie reutilizat de alți dezvoltatori, documentează explicit ce reprezintă fiecare parametru al constructorului — informație pe care semnătura singură, fără docstring, nu o comunică complet.

Unelte de generare automată de documentație (Sphinx, mkdocs) citesc exact aceste docstring-uri pentru a construi pagini complete de referință API, fără intervenție manuală suplimentară — motiv adițional pentru care biblioteci publice mari, folosite de mii de dezvoltatori externi, investesc consistent în docstring-uri complete și corecte pentru fiecare clasă și metodă publică expusă.

## REVEAL

{/* TABLE */}

| Element din cod PyTorch | Ce reprezintă |
|---|---|
| `class Model(nn.Module):` | Definire clasă + moștenire din clasa părinte PyTorch |
| `def __init__(self, ...):` | Constructor — rulează la creare, inițializează starea |
| `super().__init__()` | Inițializează corect partea din clasa părinte, obligatoriu primul pas |
| `self.strat = nn.Linear(...)` | Atribut de instanță — un strat specific acestui model |
| `def forward(self, x):` | Metoda care definește propagarea înainte |
| `model(x)` | Apelare implicită prin `__call__`, care rulează `forward()` intern |

<FactBox>
**Clase în cifre:**
- `self`: transmis automat de Python la fiecare apel `obiect.metoda(...)` — nu se pasează explicit
- `super().__init__()`: obligatoriu primul apel în `__init__` al oricărei subclase `nn.Module`
- Name mangling (`__atribut`): redenumire internă automată, nu o restricție de acces reală ca `private` din Java
- `nn.Module.__call__`: mecanismul care face `model(x)` echivalent (dar mai sigur) cu `model.forward(x)`
- Convenția underscore simplu (`_atribut`): semnal de intenție, nu impunere tehnică
- Fiecare instanță are propriile atribute independente — modificarea unei instanțe nu afectează altele
</FactBox>

## ÎNCHEIERE

O clasă combină date (atribute) și comportament (metode) într-o singură unitate reutilizabilă. Moștenirea (`class X(Parinte):`) permite construirea de comportament specializat peste o fundație generică deja scrisă — exact mecanismul prin care fiecare model PyTorch obține, gratuit, urmărirea automată a parametrilor și integrarea cu restul framework-ului, doar prin extinderea `nn.Module`. Metodele speciale (`__init__`, `__repr__`, `__eq__`) și distincția dintre `@classmethod`/`@staticmethod` completează fundația necesară pentru a citi confortabil orice clasă Python întâlnită în cod real de AI.

Ai văzut list comprehensions menționate de câteva ori deja, fără sintaxa completă. Lecția următoare dedică timpul necesar exact acestui pattern — construirea concisă de liste noi din altele, o unealtă pe care o vei folosi constant, inclusiv la procesarea datelor pentru orice pipeline de AI, adesea combinată direct cu buclele și structurile de date deja acoperite în lecțiile anterioare ale acestui curs.
